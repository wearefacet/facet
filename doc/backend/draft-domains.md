# Draft Domains

**Files:** `src/domain/`, `data/seeds/core.Domain/definition.yml`, `src/doctype/create.cr`, `src/doctype/update.cr`, `src/document/update.cr`, `src/replication/registry.cr`, `src/replication/validator.cr`, `src/http/server.cr`, `src/rbac/principal.cr`, `src/rbac/auth_context.cr`, `src/rbac/preview_enforcer.cr`, `src/iam/jwt.cr`, `src/http/auth_handler.cr`, `src/domain/routes.cr`

A draft domain is a throwaway `core.Domain` document with `draft = true`. It lets a user design and iterate on doctypes (via the doctype editor or AI assistant) without the append-only / migration discipline that governs live domains. When ready, the user **publishes** the draft: a fresh real-named domain is created with the draft's structure, and the draft's data is discarded.

**The draft path is not the only way a domain is born.** A principal holding `write core.Domain` may also create a live domain directly: `POST /Api/core/Domain` (the generic document route) takes the domain id from the body (`id` or `domain` key; a body without either answers 422), creates the domain with `event: "created"`, and auto-grants the creator as domain editor. A re-POST for a **live** domain answers 409 — `Domain '<id>' already exists` — and appends nothing: the original content and its single `create` mutation stand, exactly like the duplicate-registration guard on `POST /Api/core/DocType`. A **dropped** (tombstoned) domain may be re-created under the same id: the create projection trigger resurrects the row. There is no `/check` gate and no version gate on this path — it is the plain document-create contract, and any agent tooling may use it when it wants a live domain without the draft iteration loop. The draft → author → publish flow remains the recommended lifecycle for interactive authoring: it is the only path with diagnostics (`/check`), the version gate on publish, and throwaway iteration. See [`build-a-domain.md`](../ops/build-a-domain.md) for both recipes end to end.

Phase 1 scope: **new, empty drafts only.** Forking an existing live domain into a draft, and migration-gated publish of a data-bearing draft, are Phase 2 work and are not implemented here.

---

## Data model

Two fields on the `core.Domain` document:

| Field | Type | Default | Notes |
|---|---|---|---|
| `draft` | `boolean` | `false` | Set once at create time. Source of truth for all isolation and capability decisions. Written only by the publish action. |
| `source_domain` | `string` | *(absent)* | Stamped only on drafts created via `Domain::Draft.create_from` — records the live domain the draft was derived from. Used to enforce the one-draft-per-source-domain invariant. Absent on empty drafts (`Domain::Draft.create`) and on live domains. |

Both are optional, same-version additive edits to `core.Domain` — existing `core` / `iam` domains stay valid with the defaults.

### Naming

Draft domain names are **autogenerated with a `_` prefix** (`_` + unique suffix), so uniqueness is automatic and users never pick a draft name. Drafts are created via `POST /Api/core/Domain/draft` (empty draft) or `POST /Api/core/Domain/:id/draft` (draft from an existing live domain's structure).

**The `_` prefix is cosmetic only.** Every filter, guard, and branch keys off the `draft = true` boolean — never off the prefix. Do **not** write `LIKE '_%'` anywhere.

The `core.Domain.name` field ("Domain Name") is the publish-target name the author intends the draft to take. It is constrained by the same regex as the live domain contract — `^[a-z][a-z0-9\-]*$` (lowercase alphanumeric with dashes, starting with a letter) — so an authoring-time typo (uppercase, spaces, underscores, punctuation) is rejected at PATCH time with a `422` `invalid_format` validation error, rather than surfacing as a publish-time `422` from `Domain::Publish.validate_target_name`. Publish itself takes `target_name` from the request body, not from this field, so the two checks are independent defences-in-depth.

The `core.Domain.label` field ("Label") is the human display name the interface shows instead of the name. It is free text (max 64 chars); every surface falls back to `name` when it is absent or empty. The create-domain dialog infers the id from the label (lowercase, dashes); the label carries over to the published domain with the rest of the document content.

## State machine (safety-critical)

- `draft` is set once, at create time, by `Domain::Draft.create` (empty draft) or `Domain::Draft.create_from` (structure-copy draft).
- The only legitimate transition is `draft: true → false`, performed **only** by the publish action. In Phase 1, publish creates a *new* domain and drops the draft, so in practice the draft domain is hard-deleted rather than flipped.
- **`published → draft` does not exist in the model.** You never toggle a live domain into draft; you create a new draft. There is no code path that writes `draft = true` onto an existing published domain.

### Guard

`Document::Update` rejects `draft` appearing in any patch diff against a `core.Domain` document. The create side mirrors the guard: the generic `POST /Api/core/Domain` route rejects any body that carries a `draft` key (422), so a draft with a caller-chosen id is impossible — drafts exist only through the two services below. The update guard is enforced as an explicit rejection branch in `src/document/update.cr` (via `reject_draft_patch?`) — not via `read_only` field semantics, which are less visible and less surgical.

---

## Capability switch — `Doctype::Update` and `Doctype::Create`

Both `Doctype::Update` and `Doctype::Create` detect the target domain's `draft` flag and switch to the draft-mode validation path when `draft = true`. `Doctype::Update` reads the flag via `SELECT ... FOR UPDATE` on the `core.Domain` projection row, inside the update's transaction. This serialises against the publish action's write/delete of the same row, eliminating any TOCTOU. `Doctype::Create` reads the flag without `FOR UPDATE` (no row to lock against — the doctype is being created, not mutated).

If `draft = true`:

- `validate_version` constraints are skipped (version may decrease or skip ahead).
- `check_same_version_guards` are skipped (field removal / type change allowed — implied `$force`).
- Migration-function requirements on version bumps are skipped.
- Domain-name regex is relaxed to permit the `_` prefix (`validate_domain_name_draft`).
- Schema is otherwise validated (field names, action names, script compiles, etc. all still enforced).
- The doctype definition is overwritten freely.

**No mid-draft truncation.** History is kept during draft (simpler code path). The dirty log — versions that decreased, destructive same-version edits, gaps with no migration function — never crosses into published mode because publish copies *structure only* and drops the draft's data entirely. Invariant violations stay quarantined inside the draft and die with it.

Non-draft domains take the existing path unchanged.

**Stale-definition window.** Definition-cache invalidation is asynchronous: the save enqueues its `core.DocType` event, and `Subscriber::DoctypeCache` marks `Doctype::DefinitionStore` stale only after the post-commit flush delivers it. A document write that lands within about 1 to 2 seconds of a definition save can still run the old definition — in the authoring loop (save the definition, then test at once), a stale compute can read as a failed fix; re-test after a short wait before you judge the script.

## Isolation

Drafts must not be referenced by live domains. Enforced at two points:

1. **`Replication::Registry#fetch_all_doctype_definitions`** filters out doctypes whose domain has `draft = true`, via an `EXISTS` subquery against the `core.Domain` projection row. This is the structural runtime cut: draft doctypes never appear as replication sources or consumers, so nothing downstream in the registry ever sees them. The draft's own bindings are dropped as a consumer; with no consumer, the source never enters `source_doctypes` either.

2. **`Replication::Validator`** is the authoring-time guard: a live-domain `replicate` config whose source domain is a draft is rejected with a clear error at doctype create/update time. Defense-in-depth on top of the registry filter.

**Out of scope for isolation:** WebSocket is **not** cut (the WS path is fine with draft events). No seeded author-only RBAC provisioning — the publish action is gated by the normal `write core.Domain` permission (already on the editor/admin seeded roles).

### Honest asymmetry

Because drafts are excluded as replication producers *and* consumers, replication is the one definition surface that cannot be exercised in draft. Everything else (projections, masking, views, validations, lifecycle hooks) fires for real; replication graphs do not. A draft may *declare* replicate fields (they're schema-valid), but they remain inert until publish, at which point the target is a live domain whose first doctype update runs full validation including `Replication::Validator`.

## Publish — copy-and-drop

Endpoint: `POST /Api/core/Domain/:id/publish` with body `{"target_name": "orders", "overwrite": false}`.

Optional `documents` field carries draft documents into the target:

```json
{ "target_name": "orders", "overwrite": false,
  "documents": { "import": true, "doctypes": ["Status"] } }
```

- Absent, or `"import": false` — structure only (the default).
- `"import": true` with `doctypes` absent — every doctype the draft defines.
- `"import": true` with a name list — those doctypes only. Names are bare (`Status`) or draft-qualified (`_abc.Status`).
- A name the draft does not define answers `422`.

The target must not already define a selected doctype. A fresh publish targets a free name, so every doctype is new there. An overwrite publish replaces a live domain, so a selected doctype the live target already defines answers `422` — draft rows never merge into production rows. `Publish::Result.documents_imported` reports the count, and the publish response carries it as `documents_imported`.

Authorised by `RBAC::WriteEnforcer.authorize_update(db, "core", "Domain", id, auth_context)` — the same `update core.Domain` permission that gates drafting (on the editor role, scoped to domains the account edits — see [`domain-editors.md`](domain-editors.md)). Overwrite publish additionally enforces the same gate on the **target's** `core.Domain` row inside the service: an editor must edit the target domain too, not just the draft. The draft creator (write on `core.Domain`) is also the publisher — no separate `publish` meta-permission.

Publish is **copy-and-drop**, not a rename or flag flip. `(domain, doc_type)` is the compound primary key on `projections` and `mutations`. Because the mutation log is append-only, renaming a domain in place would either rewrite historic mutation rows (breaking the audit contract) or orphan them from their own projections. Copy-and-drop avoids that: the target gets fresh rows under the new identity; the source's projections are soft-deleted.

Two modes:

- **Fresh publish** (`overwrite: false`, default): the target name must be free — 409 if a non-deleted `core.Domain` owns it.
- **Overwrite publish** (`overwrite: true`): the target may already exist. Each draft doctype whose structure differs from the live one must satisfy the **version gate** (below); identical doctypes publish as-is.

### Version gate (overwrite mode)

For every doctype `D` the draft defines, compare its definition against the live target's `core.DocType` row:

- **Live `D` absent** → new doctype — publish it (additive).
- **Structure identical** (`Doctype::Structure.equal?` — zero data-shape changes, additive ones included, and unchanged `actions`) → publish the draft definition as-is, no version requirement. `Structure.equal?` is deliberately stricter than the same-version `data_shape_equal?`: a draft that only adds a field or an enum key still needs a bump to publish over a live domain, while a presentation-only edit (label, title, default, view, compute, operators) does not.
- **Structure different** → the draft's `schema_version` must be **exactly `live + 1`** and the definition must carry a `migrations[live_version]` entry whose Lua function exists in the script. A no-op Lua migration function is acceptable. This is enforced by `Domain::PublishGate.check`, which relinks the draft onto the target identity first and then runs `Doctype::Validation.validate(definition, live_version)`; a missing migration gap reports `Migration from vN to vN+1 is missing`. Any gate failure returns 422 naming the doctype.

The gate guarantees the *definition's* migration chain is complete. Live documents are **not** migrated eagerly — they stay at their stored `meta.schema_version` and the existing lazy read-time `Document::Migrate` walks the (now-complete) chain on next read. Because the gate verified every gap has a function, lazy migration cannot fail on a missing entry.

In one transaction (`Database.with_transaction`):

1. **Validate**: target name matches `^[a-z][a-z0-9\-]*$` and does not start with `_`; source domain has `draft = true` (read with `FOR UPDATE`). The draft's whole doctype set must form a closed composition graph — every `children:` entry reciprocated by a `member_of` on its target and vice versa (`Doctype::Composition.validate`, hard `422` on a one-sided edge). For fresh publish, target name is free; for overwrite, the version gate above passes.
2. **Publish each doctype** the draft defines:
   - Fresh target → `Domain::Copy.structure(db, from:, to:, draft: false)` creates the target `core.Domain` document (with `draft: false`, preserving description/color/context_sets — the draft's `hooks` ride along in the copied content) and copies each doctype definition + its `DocumentView` children, enqueuing `created` on `core.Domain` and `registered` on `core.DocType`.
   - Overwrite target → the live `core.Domain` document is **preserved** (context_sets, description — never overwritten by the draft's copy). This includes the `hooks` field: overwrite publish does not carry the draft's hooks. When the draft declares hooks the live domain lacks, the publish response carries a `warnings` entry naming them and the server logs one WARN line; the workaround is to patch the `hooks` field on the live domain (see [`hooks.md`](hooks.md) → Publish and hooks). Each doctype definition is upserted via `Domain::Copy.upsert_doctype_definition` (`updated` event when the row exists, `registered` when new), then the doctype's `DocumentView` rows are reconciled (below).
3. **Re-run the replication invariants over the whole published set.** The authoring-time check self-skips any source it cannot resolve, so a replica-of-replica field authored before its source exists (the natural order inside a draft) lands unchecked. Once every bundled doctype has landed under the target name, the same `Replication::Validator.validate_invariants` resolves those sources: a violation — e.g. a field that replicates from a replica — refuses the publish with `422 Publish refused: … Cannot replicate from a replica.` and the transaction rolls the copy back. The check is definition-set-wide (every doctype of the target, not only the draft's), because a live doctype may hold an edge whose source resolves only once this publish lands. The advisory `/check` warning stays the backstop for out-of-order live edits.
4. **Carry the editors over.** `Domain::Editors.transfer(db, draft_id, target_name, actioner_id)` copies the draft's `core.DomainEditor` rows onto the target (skipping existing pairs) — co-editors of the draft keep their rights on the published domain. Fresh publish and overwrite both.
5. **Carry the selected documents** (when `documents` names any). Runs after the structure copy, so every target definition resolves for the document gates, and before the drop, so the draft rows are still readable. The rows flow through `Domain::Portable::Import.import_documents` — the same pass a bundle import uses — so ids, reference tokens, and `meta.parent_id` are rewritten from the draft identity to the target, and the authoring gate, the secret gate, and the `unique: true` check all run. Rows are created in `sort_order` order (or `position`, or id) so a reference list keeps its draft order. A refused row answers `422` and rolls the whole publish back. Without `documents`, draft documents are scratch and are soft-deleted, not migrated.
6. **File grant tickets** via `Grants::PublishTickets.file`: scan the published definitions + hooks for outbound cross-domain edges and file/merge a `core.DomainGrant` ticket into each live producer's subtree (D11 verdict resolved against the caller; widening an active grant drops it to inactive unless the publisher holds the acceptance right). The per-producer outcome rides `Publish::Result.grant_tickets` → the publish response's `grant_tickets` → the publish dialog's report. See [`domain-grants.md`](domain-grants.md) → Publish flow.
7. **Drop the draft** via `Domain::Scratch.drop`: soft-delete the draft's doctype definitions, its `core.Domain` document, its `core.DomainEditor` rows, and all of its `projections` rows (set `deleted_at`). The `mutations` table (append-only event log) is left intact — the draft's history stays in the log for audit. The domain's managed indexes and field statistics objects are dropped (`Index::Manager.dispose_domain_indexes`), then its `doctype_indexes` rows are hard-deleted (orphan-free cleanup of index tracking).
8. **Commit.**
9. **Post-commit**: `Event::Publisher.flush` delivers the `core.Domain` `created` event
   (fresh publish) and each `core.DocType` event enqueued during the copy step.
   The `Subscriber::DoctypeCache` Pub/Sub subscriber (on `fanout:core.DocType:*`)
   receives each `core.DocType` event and **invalidates** both the doctype
   definition cache (`DefinitionStore.invalidate`) and the replication
   registry (`Replication::Manager.instance.try(&.mark_registry_stale)`).
   The next registry read rebuilds lazily from the DB — no eager refresh on
   the publish path, no separate invalidation is needed.

### DocumentView reconciliation (overwrite mode)

`core.DocumentView` rows are part of the doctype definition (one per `(doctype, kind)` — `view`, `form`, `inline`, `card`, `quickView`). On overwrite publish the live view set converges to the draft's:

- Draft view `kind` matches a live view `kind` → update the live row in place when the `template` differs.
- Draft-only `kind` → create a new live view (fresh ULID, `parent_doctype`/`meta.parent_id` rewritten to the target).
- Live-only `kind` → delete the live view (it is no longer part of the definition).

`core.CollectionView` rows (saved listing tabs) are **never touched** by publish — they are live-authored (created/edited in the live app, often owner-bound) and out of scope for the domain definition. Only `DocumentView` is definition-owned.

**Crash semantics:** copy-then-drop within one transaction. A crash before commit rolls back to an intact draft with nothing half-published; the operation is retryable (fresh: target didn't get created; overwrite: the live doctype rows are unchanged).

**Index DDL note:** `Index::Manager.sync` runs `CREATE INDEX CONCURRENTLY` in background fibers outside any transaction. If publish triggers index sync for the new domain's doctypes before commit and the txn then rolls back, the background index DDL is not rolled back. This is consistent with existing `Doctype::Update` behaviour (best-effort) and a known tradeoff; if it becomes a problem, index creation can be delayed to after-commit.

## `Domain::Copy.structure`

```crystal
Domain::Copy.structure(db, from : String, to : String, draft : Bool, actioner_id : String = "system:publish") : Nil
```

The reusable structure-copy primitive. Phase 1 publish runs it `from: "_abc", to: "orders", draft: false`, with **no data copy**. Phase 2 fork will run the inverse (`from: liveDomain, to: "_xyz", draft: true`) **with** a data-copy step. Phase 2 promote will run it real→real with a migration-gated data copy.

Copies are persisted via direct `Mutation::Client.create` (not `Doctype::Create`) to keep the copy path a single tight loop over each source doctype without per-row service overhead. (`Doctype::Create` is now draft-aware — the `_` prefix is accepted in draft mode — but `Domain::Copy.structure` still uses `Mutation::Client.create` directly because it needs to rewrite the `domain` field of each definition during the copy, which is a structural mutation the service layer does not expose.) After each doctype copy, `Index::Manager.sync`, `DefinitionStore.invalidate`, and `Event::Publisher.enqueue("registered")` are called — mirroring `Doctype::Create` — so the new domain's reference indexes, cache, and event subscribers (doctype-cache, replication registry) stay consistent. The target `core.Domain` document's `created` event is enqueued in the same way.

`Domain::Copy.upsert_doctype_definition(db, content, doctype_name, to, actioner_id, event)` is the shared persist primitive behind fresh publish, overwrite publish, and the import branch that creates a bundled doctype (`Domain::Portable::Import`): it takes the raw definition JSON, rewrites the `domain` field to `to` and **relinks same-domain reference targets** (below), then creates the `core.DocType` row when absent (`event: "registered"`) or updates it in place via a full JsonDiff when present (`event: "updated"`). An overwrite of a structurally identical doctype diffs to empty — the update branch skips the no-op mutation (and its event) instead of raising `Mutation::Client.update`'s empty-diff error; identical doctypes publish as-is. In both cases it runs `Index::Manager.sync`, `DefinitionStore.invalidate`, and enqueues the event.

### Reference-target relink

Both persist primitives rewrite through `PublishGate.domained_content(content, to)`, which does two things: it sets `domain` to the target, and it **relinks reference targets** — every `reference`-typed field (including `items`, `properties`, and dictionary `values` sub-schemas) whose declared `doctype` starts with the definition's own `{domain}.` is re-pointed to `{to}.`. Cross-domain targets (e.g. `iam.Account`) are untouched. The relink is what makes publish safe for schemas with internal references: a draft declaring `doctype: "_06gny26yz8c2.Brand"` publishes as `doctype: "orders.Brand"`, while the draft identity is dropped by `Scratch.drop`. The inverse copy gets the same treatment — `Draft.create_from` (live → draft) relinks `orders.Brand` to `{draft}.Brand`, so the draft is a self-contained sandbox and a publish round-trips the targets back to the target identity. The same rewrite covers the portable import `--into` rename. The gate (`PublishGate.check`) judges the relinked definition, so a draft derived from a live domain whose only difference is the relink stays structurally equal and publishes without a `schema_version` bump.

What the relink does **not** rewrite: declared targets pointing at other domains, `children`/`member_of` (bare same-domain names by rule), `replicate` configs (`{via, field}` — no domain), and literal values embedded in named scopes, reference `filter` values, view templates, or Lua scripts. Those literals name document ids, which are scratch and do not survive publish — relinking the prefix would only trade one dangling id for another.

After each doctype definition is copied, its owned children (`core.DocumentView`, `core.CollectionView`, etc.) are copied via `Document::Copy.copy_children_of`. The `core.DocType` definition declares `children: document_view → DocumentView` and `children: collection_view → CollectionView`, and both child doctypes declare `member_of: DocType`, so the recursive copy discovers and copies every child belonging to the source doctype. Each copied child gets a fresh ULID doc_id, its `meta.parent_id` is remapped to the target doctype's id (`{to}.{doctype}`). `core.DocumentView` additionally has a `parent_doctype` content field that is rewritten accordingly; `core.CollectionView` has no such field — it relies solely on `meta.parent_id`. This carries the full doctype configuration — not just the field schema — into the target domain.

## `Domain::Scratch.drop`

```crystal
Domain::Scratch.drop(db, domain : String) : Nil
```

Soft-deletes everything owned by the draft domain. **Refuses to run unless the domain's `draft = true`** (fail-closed — raises `Scratch::Error`). Used only by publish.

The `mutations` table (append-only event log) is **never touched** — the draft's history stays in the log for audit purposes. Only `projections` (materialised view), `doctype_indexes` (index tracking), and the artifact provenance tables are modified. Projections are soft-deleted via `deleted_at`, matching the normal `Document::Delete` behaviour; all consumers already filter `deleted_at IS NULL` so the draft's documents disappear from every query surface. Disposes:

- `doctype_indexes` rows for the domain (hard-deleted — orphan-free cleanup of index tracking rows). The physical indexes and field statistics objects those rows describe are partial DDL on the shared `projections` table, so they are dropped first (`Index::Manager.dispose_domain_indexes`, non-concurrent because disposal runs inside a transaction). Deleting the tracking rows alone would leave the real indexes behind, and nothing would ever drop them again — every write and query plan would keep paying for a domain that no longer exists.
- `projections` rows where `domain = $1` — the draft's own document data (soft-deleted).
- `projections` rows under `domain = 'core'` keyed by `content->>'domain' = $1` — the draft's `core.DocType` definition rows (soft-deleted).
- `projections` rows under `domain = 'core'` keyed by `content->>'domain' = $1` on `core.DomainEditor` — the domain-editor rows pointing at the dropped domain (soft-deleted), so no grant ever references a dead slug. Covers publish-drop, draft discard, and `Domain::Drop` (all funnel through `dispose!` → `dispose_definitions!`). See [`domain-editors.md`](domain-editors.md).
- `projections` row for the draft's own `core.Domain` document (soft-deleted).
- `artifact_owners` and `artifact_references` rows for the domain (hard-deleted — provenance is domain-scoped; `artifact_grants` cascade via `owner_id → artifact_owners`). The `artifacts` rows themselves are left untouched — they fall out on the next prune, whose eligibility is join-derived (see [`artifact.md`](artifact.md) → Prune).

Snapshots live in the `mutations` table (not a separate store); the search side-channel is a per-transaction GUC (`set_config(..., true)`), not persistent state. Soft-deleting projections + hard-deleting `doctype_indexes` makes the draft invisible to all query surfaces while keeping the audit log intact.

## `Domain::Drop`

```crystal
Domain::Drop.call(db, domain_id : String, actioner_id : String) : Result | Facet::ServiceError
```

**Files:** `src/domain/drop.cr`, `src/domain/routes.cr` (`handle_drop`), `src/document/delete.cr` (generic-DELETE refusal).

Deletes a domain — draft **or** live — through the same teardown mechanism (`Scratch.dispose!`, full scope) plus an audit record: a `delete` mutation is inserted on the `core.Domain` document **before** the teardown, so the projection trigger tombstones the Domain row through the normal path and the audit log shows the actor. Runs in one transaction — either the whole domain disappears or nothing does.

Guard rails (fail-closed):

- System domains (`core`, `iam`, `app` — the seeded bootstrap domains) are refused with 422.
- A live domain with an open draft branched from it (the draft's `source_domain` points at it) is refused with 409 — discard the draft first.
- Unknown or already-deleted domains return 404.

The generic document route `DELETE /Api/core/Domain/:id` returns 422: tombstoning only the Domain document would orphan the domain's definitions, data, views, and index rows. Domain deletion must go through the drop endpoint.

Cross-domain note: reference fields in *other* domains that pointed at this domain's documents dangle after a drop — the same accepted behaviour as deleting any referenced document (`Document::Delete` does not check incoming references).

## `Domain::Draft.create`

```crystal
Domain::Draft.create(db, body : String, actioner_id : String) : Result | Error
```

Creates a new empty draft domain document. Autogenerates a `_`-prefixed unique name (ULID-based) and forces `draft: true`, ignoring any `id`, `domain`, or `draft` field the caller tries to supply. Gated by `RBAC::WriteEnforcer.authorize_create(db, "core", "Domain", auth_context)` at the HTTP layer. The creator is recorded as the draft's first domain editor (`Domain::Editors.grant`, same transaction) — see [`domain-editors.md`](domain-editors.md).

The door writes through `Mutation::Client` directly, so it validates the `name` and `label` content fields against the `core.Domain` definition's fields of the same keys (type, length, pattern) before the mutation insert — the same check a later PATCH applies, so a value the update door would reject never lands on the draft. The check is skipped when the definition is not registered; publish still validates the live target name.

## `Domain::Draft.create_from`

```crystal
Domain::Draft.create_from(db, source_id : String, actioner_id : String, auth_context : RBAC::AuthContext = RBAC::AuthContext.system) : Result | Error
```

Creates a draft from an existing **live** domain by copying its structure (doctype definitions + `core.Domain` document + each doctype's `DocumentView` templates) into a new `_`-prefixed draft via `Domain::Copy.structure`, stamping a `source_domain` provenance field on the new draft's `core.Domain` document. **No document data is copied** — structure only, the same primitive publish uses. Used by the frontend's "Edit existing domain" action in builder mode. The creator is recorded as the draft's first domain editor (`Domain::Editors.grant`, same transaction) — see [`domain-editors.md`](domain-editors.md).

A scoped `create core.Domain` caller must also be an editor of the source domain — `Domain::Editors.authorize_draft_from?` answers 403 otherwise, because drafting forks the source's definition surface. Wildcard roles and the system bypass pass; internal callers default to the system bypass (the `Publish.call` convention). The fresh-draft route (`create`, no source) keeps create-then-own: any caller with `create core.Domain` may open a draft, and the creator becomes its editor in the same transaction.

### Guard: one draft per source domain

At most one draft may exist per source live domain at any time. Enforced by checking no draft (`content->>'draft' = 'true'`) with `content->>'source_domain' = source_id` already exists — reject 409 if it does. Empty drafts (`create`, no source) are unconstrained.

### Source validation

- 422 if the source domain does not exist.
- 422 if the source is itself a draft (drafts are scratch — drafting a draft is not meaningful).

## HTTP surface

| Method | Route | Purpose |
|---|---|---|
| `POST` | `/Api/core/Domain/draft` | Create an **empty** draft domain (autogenerates `_`-prefixed name, sets `draft: true`). Body is the optional domain content. Gated by `write core.Domain`. |
| `POST` | `/Api/core/Domain/:id/draft` | Draft a **live** domain into a new draft (structure copy, no data). Stamps `source_domain = :id` on the new draft. Rejects 422 if source missing or is itself a draft; 409 if a draft already exists for this source; 403 when a scoped `create core.Domain` caller does not edit the source domain. Gated by `write core.Domain` plus the source-membership gate. |
| `GET` | `/Api/core/Domain/:id/check` | Aggregate diagnostics for a domain — runs `Doctype::Check` for every non-deleted `core.DocType` whose `content->>'domain' = :id` and combines the per-doctype issues. Adds domain-level `:no_doctypes`. Used by the Builder landing page (issue-count chips) and the draft DomainEditor's Check tab + Publish confirmation. Gated by `write core.Domain` on the target. |
| `POST` | `/Api/core/Domain/:id/publish` | Publish a draft into a real-named domain. Body: `{"target_name": "…", "overwrite": false}`. `overwrite: true` allows publishing over an existing domain subject to the version gate. The response carries `domain`, `grant_tickets`, and `warnings` (one entry when an overwrite publish does not carry draft hooks the live domain lacks — the live `core.Domain` document is preserved). Gated by `write core.Domain` on the draft. |
| `POST` | `/Api/core/Domain/:id/preview-session` | Issue a preview-mode capability token scoped to a draft domain. The caller proves, against their real identity, that they may edit the draft's definition (gated by `update core.Domain` on the draft row — where the editor role's `$domain_editor` scope bites). Returns `{token, preview_domain, expires_at}`. Rejects non-draft domains (422), unknown drafts (404), and `system`/`denied`/`preview` callers (403) — a capability token must be attributed to a real account. |
| `POST` | `/Api/core/Domain/:id/drop` | Delete a domain (draft **or** live). Full-scope teardown plus a `delete` mutation on `core.Domain` for audit. Refuses system domains (422), live domains with an open draft (409), unknown domains (404). Gated by `delete core.Domain`. See `Domain::Drop` above. |

These mirror the `put /Api/core/DocType/:id` precedent — dedicated Crystal endpoints rather than Lua actions, because publish needs to soft-delete projections across multiple domains and hard-delete `doctype_indexes` rows (something the Lua `document.*` helpers can't do, and something that doesn't fit the `Document::Action` flow which computes a single-document diff).

## `Domain::Check`

**File:** `src/domain/check.cr`

Aggregate diagnostics for a single domain. Runs `Doctype::Check.call` for every non-deleted `core.DocType` projection whose `content->>'domain' = $1` and collects the per-doctype issues into one result. The service is read-only and accepts either live or draft domains — the only consumer today is the Builder (draft domain editor's Check tab + landing page issue chips), but the endpoint is generic.

Adds one domain-level diagnostic beyond what `Doctype::Check` surfaces:

- `:no_doctypes` — the domain has zero registered, non-deleted doctypes. Useful for the publish-flow UX so an empty draft can be flagged "nothing to publish".

Per-doctype results split `Doctype::Check` output into two lists: `issues` (warning- and error-severity, the actionable diagnostics — the aggregate's `issue_count` counts only these) and `notices` (informational notices: the `:defaults` notices for an absent `display_name` template / `search` template, and the missing standard view kinds). Notices never count toward the publish-warning count — a fresh doctype with no views checks clean on the schema. One exception: an **aggregate root** that declares neither a `display_name` nor a `search` template is invisible to every search surface, so `Doctype::Check` raises a `:defaults` **`:error`** for that case, and it counts toward `issue_count` (B-296). An owned child in the same state is an `:info` notice — it is reached through its parent.

A doctype whose stored definition fails to parse (corrupt `schema_version`, malformed body) is caught and surfaced as a single `:composition` warning rather than letting the whole aggregate call raise — a single bad doctype should not block diagnostics for the rest of the domain.

`Facet::Domain::Check.call(db, domain)` returns `Result | Error`. `Error` (404) when the `core.Domain` document does not exist or is deleted. Authorisation is the caller's responsibility (the HTTP route gates it via `RBAC::WriteEnforcer.authorize_update` against `core.Domain`, mirroring `/publish`).

## Preview mode

A preview session lets the drafter interact with a draft domain's documents through the standard `/Api/:domain/:doctype/...` routes — i.e. exercise views, run named actions, create/edit/delete documents, and observe the live application's rendering — exactly as they would against a published domain. The pipeline is:

1. The frontend enters the Builder preview subtree (`/Builder/:draft/preview/[...path]`, present today as a seam) and calls `POST /Api/core/Domain/:id/preview-session` to obtain a short-lived capability token.
2. From then on, every request the live application issues carries the preview token under `Authorization: Bearer <token>`. The standard `/Api/:domain/:doctype/...` routes resolve the draft domain straight from the URL (the `_` prefix is already a real domain name on the projections table) — no rewrite layer, no proxy.
3. The `AuthHandler` branches on the token's `typ: "preview"`, loads the named `preview_domain`'s `core.Domain` projection, verifies `draft = true` (defense-in-depth — a published-then-dropped draft's token fails closed immediately), and constructs an `AuthContext.preview(account_id, preview_domain)`.
4. The standard enforcer branch (`RBAC::PreviewEnforcer`) authorises the operation purely on domain identity:
   - **Inside the draft domain** — every CRUD action plus named actions is allowed. No named-scope resolution; the draft has no production-tuned scopes and the user is concurrently editing the schema. Field-level masking is skipped (the drafter must see every field).
   - **Cross-domain references into live domains** — denied. Preview tests *your draft's* behaviour against scratch data; production data is never surfaced through a draft's reference fields. The live app shows its standard permission-denied affordance on the unsupported reference cell.
   - **`core.DocType` writes** (PUT /Api/core/DocType/:id, schema edits) and **`core.Domain` writes** (publish/discard) — denied. Schema edits go through the Builder editor on the caller's real role; preview is data-only.
   - **`core.DocType` lists** (`GET /Api/core/DocType?items=500`, used by `DoctypeRegistry` to build the nav model) — allowed, scoped by an emitted `content->>'domain' = $N` clause so only the bound draft's rows surface. Same for **`core.Domain` lists**, scoped by `id = $N` so the live nav surfaces the draft's row alone. Without these carve-outs the live application's nav list would be empty during preview.
   - **`core.Domain` single-doc reads** (`GET /Api/core/Domain/:id`) — allowed when `doc_id` equals the bound draft domain. The live dashboard's fall-back fetch when entering `/_abc` during preview (see `routes/[domain=notApi]/+page.ts`'s carve-out) reads the bound draft's own Domain projection; without this row-level gate the default `domain == preview_domain` rule would deny (the draft id is the row's id, not its `domain` column), surfacing as a non-disclosing 404.
   - **`core.DocType` single-doc reads** (`GET /Api/core/DocType/:id`) — allowed when the row's `content->>'domain'` equals the bound draft. Mirrors the list carve-out at the row level so the live app reading `/Api/core/DocType/_abc.Widget` authorises.
   - **`core.DocumentView` / `core.CollectionView` reads** (children of `core.DocType`) — allowed *only* when the row's parent `core.DocType` belongs to the bound draft. The live application reads these rows to render listing tabs and document templates; without the carve-out, preview would have no UI. Writes stay denied.

The capability model: you proved at preview-session issuance that you can edit the draft's doctype definitions; from then on, the preview token grants all four CRUD actions on that draft's documents, attributed in the mutation audit log to your real `account_id` (not "preview", not "system").

**The builder assistant stays available during preview.** The live routes mount the builder assistant (not the workspace one) while a preview session is active, so the user keeps iterating on the draft from the chat window while looking at the preview. The conversation-create route accepts the preview capability and binds the conversation to the token's draft (see [`assistant.md`](assistant.md) → Auth model); the schema edits ride the system-tier registrar exactly as in the builder editor — the preview token itself never gains schema-write reach. Streaming and the read surfaces pass unchanged: the ownership and usage gates key on the account id the preview token carries. The sidebar and the open page hot-reload while the assistant mutates the draft: the root layout keeps the builder WebSocket subscription alive during preview (the socket is cookie-authenticated, so the real principal — the same subscription the builder editor uses) and rebuilds the nav from the preview-scoped REST surface on every collection event.

**Files:** `src/rbac/principal.cr` (`Principal::Preview`), `src/rbac/auth_context.cr` (`AuthContext.preview`), `src/rbac/preview_enforcer.cr`, `src/iam/jwt.cr` (`PREVIEW_TOKEN_TYP`, `build_preview_payload`), `src/http/auth_handler.cr` (`build_preview_auth_context`), `src/domain/routes.cr` (`handle_create_preview_session`).

## Phase 2 boundary (out of scope, named so it isn't assumed free)

1. **Doctype removal on publish** — a live doctype that the draft no longer defines is left alone (publish only touches doctypes the draft defines). Deleting a doctype with live data is deliberately out of scope; it needs its own deletion semantics and a migration story.
2. **Data-bearing fork** — copying a live domain's document data into a draft, not just its structure. `Domain::Copy.structure` already excludes data by design; a data-bearing variant would layer a copy step on top and needs migration handling on publish-back. Not implemented.
