# Backend Workflow

Referenced by [`AGENTS.md`](../../AGENTS.md) when a task touches Crystal backend code (`src/`, `spec/`, `db/`, `lib/`, etc.).

---

## Crystal conventions

- Modules under `Facet::` namespace.
- Separate concerns into files (one concept per file).
- Use Crystal's type system (no runtime type puns where avoidable).
- Keep functions small, single-purpose.
- Use the existing dependency stack (Kemal, PG, Lua) — only add new shards when the task genuinely requires it.
- Use `.as(Type)` instead of `.not_nil!` for compiler-guaranteed non-nil values.

## Build & run (Makefile)

The backend exposes a small Makefile at the repository root wrapping the common Crystal invocations. **Prefer these targets over calling `crystal` directly** — they pin the entry point (`src/main.cr`) and the canonical flags so contributors don't have to remember them.

| Target           | Equivalent                                  | Purpose                                                              |
| ---------------- | ------------------------------------------- | -------------------------------------------------------------------- |
| `make test`      | header check → `crystal build -o build/spec_run <spec files>` → `./build/spec_run --fail-fast` | Header gate, then the Crystal spec suite (aborts on the first failing example). The license check runs first — it fails in under a second, before the test database starts. The suite is built first and run as a separate process (see Testing below). `FAIL_FAST=` drops `--fail-fast`; `SPEC_FLAGS=...` adds runner flags |
| `make test_build` | `crystal build --no-debug -o build/spec_run <spec files>` | Compile the spec suite into `build/spec_run` without running it (skipped when no source changed). Re-run selections with the runner flags: `./build/spec_run -e "Document::Create"`, `./build/spec_run --profile -e "Document"`, `./build/spec_run --location spec/document/create_spec.cr:117`. Removes the ~60 s compile from every iteration |
| `make check`     | `crystal build src/main.cr --no-codegen`     | Type-check / build without emitting a binary (fastest compile gate)  |
| `make build`     | `crystal build src/main.cr -o build/facet` | Build the dev server binary into `build/`                            |
| `make build_release` | `crystal build src/main.cr --release -o build/facet-release` | Release-optimized build into `build/`                                |
| `make run`       | `crystal run src/main.cr -- server`         | Run the dev server (no build artifact)                               |
| `make clean`     | `rm -rf build/`                             | Remove the `build/` directory                                        |
| `make license_check` | `scripts/check-license-headers.sh`      | Fail when a first-party source file misses the SPDX header (same check CI runs as its `License headers` step) |

The Makefile is **backend-only**. The frontend lifecycle (`pnpm dev`, `pnpm build`, `pnpm test`, `pnpm check`, …) stays driven by `frontend/package.json` — see [`doc/frontend/workflow.md`](../frontend/workflow.md). For the full dev experience (migrate + backend + frontend in parallel) use [`./scripts/dev`](../../scripts/dev); `make run` only starts the backend.

`make check` is a compile gate (Crystal semantic analysis + LLVM IR, no machine code). It is **not** a linter — style checks still run via `bin/ameba` (see below).

## Linting

Run `bin/ameba` before and after testing. Split large methods to stay under cyclomatic complexity thresholds.

## Testing

- **Run the full suite only when you finish the task.** `make test` compiles and runs every spec file and takes 10 minutes or more. While you write code, run only the specs that cover your change. Two ways to do that:

  - `crystal spec spec/<dir>/<file>_spec.cr` (one file) or `crystal spec spec/<dir>/<file>_spec.cr:LINE` (one example). Passing one explicit file to `crystal spec` is fine — the sorted-file-list rule below only applies when you pass many files. One limit of single-file runs: the file compiles alone, so its require tree must be complete. If a first-party file in the tree references a constant from a module the tree does not require, the compile fails. Example: `spec/assistant/stream/session_spec.cr` alone fails on `Facet::MCP::PATH_PREFIX` (`src/http/auth_handler.cr` references it; the tree misses `src/mcp`). Compile the file together with a spec that requires the missing module (any `spec/mcp/*` file), or run the full suite.
  - **Faster: build once, run many times.** `make test_build` compiles the whole suite into `build/spec_run` (about 60 s, skipped when no source changed). Every later selection then starts in under a second, with no compile step: `./build/spec_run -e "Document::Create"`, `./build/spec_run --profile -e "Document::Update"`, `./build/spec_run --location spec/document/create_spec.cr:117`. The binary takes the same runner flags as `crystal spec` (`-e`, `-l`, `--profile`, `--fail-fast`, `--junit_output`) but not file paths — select with `-e`/`--location` instead. This is the recommended loop when iterating on one area.

  The test database must be up for any spec run: `make test_db_up` starts it (idempotent; leave it up between runs). Run `make test` once at the end, as the final gate before you mark the task complete.

- **Never use `before_all` hooks.** `before_all` is fundamentally broken in this project:
  - The Kemal handler chain is a singleton — calling `call_api` or `Kemal.config.setup` inside `before_all` reassigns `next` pointers on handler instances that may still be walked, causing stack overflows.
  - `before_all` runs outside the per-test DB lifecycle (template clone + global truncation). Any data seeded in `before_all` is wiped by the global `before_each` truncation, making the hook silently useless.
  - Inside a spec file compiled together with Kemal, a bare `before_all` resolves to **Kemal's HTTP-filter macro, not Spec's hook** — the block is registered at load time to run on *every request* through the `FilterHandler`. A `Facet::Config.reset!` inside such a block nils the config singleton mid-request (observed: a login route saw its config swap evaporate and silently reloaded defaults). Use `before_each` for one-time-looking setup; it is fast.
  - Use `before_each` for setup (it's fast — the global truncation is the only overhead) or inline setup inside individual `it` blocks.

- **Database lifecycle per worker process:**
  - The suite runs against a throwaway PostgreSQL instance on host port 5433 (`compose.test.yml`; started by `make test`, which `make test` runs first) — see [`doc/backend/test-database.md`](test-database.md).
  - `Spec.before_suite` creates a shared `facet_test_template` database (migrate + seed all core doctypes/documents), protected by PG advisory lock for multi-worker safety.
  - Then it clones the template into `facet_test_worker_<pid>` and sets `DATABASE_URL` to the worker's private DB. Each worker process gets full isolation — no connection churn between examples.
  - `Spec.before_each` (global, fires before any local `before_each`) truncates `mutations` and `projections` with `RESTART IDENTITY CASCADE`. It reuses one per-worker connection (`TruncateConnection` in `spec_helper.cr`), reopened automatically when a spec changes `DATABASE_URL` (the `migrate/*` specs point it at a scratch database), so there is no per-example connection churn.
  - `Spec.after_suite` drops the per-worker DB (with `pg_terminate_backend` to kill stragglers).

- **Per-example seeding is scoped, or a snapshot restore — never a full corpus re-seed.** The global truncation wipes `projections`, so specs that write through the document pipeline must re-ensure the definitions they need: call `Facet::Doctype::Seed.ensure_doctype(db, domain, doctype)` for each doctype the file touches (`ensure_doctype_definition` when only the definition must exist; `ensure_seed_roles_with_dependencies` from `spec/support/iam_helper.cr` when the seeded role documents are needed — their permission scopes validate against registered doctypes). When a spec needs the whole seeded corpus (reference targets, domain-editor RBAC, the seeded views), call `restore_seeded_baseline(db)` (`spec/support/seeded_baseline_helper.cr`) — it copies the seeded rows back from snapshot tables taken once per suite, in one transaction (~13 ms). Do **not** call `Seed.seed(db)` per example: the full corpus re-seed runs the whole mutation pipeline and costs ~320 ms per call. Specs that test `Doctype::Seed` behaviour itself (seed projection staging, seeded view children, view idempotency) are the exception — they call the real `Seed.seed`. `Seed.document_exclusions` pins `core.Currency` for the suite — money validation reads the in-memory registry (`register_seed_currencies`, set up in `spec_helper.cr`), so specs never need the currency rows; the DB-coupled path is covered by `spec/currency_spec.cr`, which seeds its own rows.
- **The suite never resolves DNS.** `Webhook::TargetCheck` exposes a swappable `resolver`; `with_fake_resolver` (`spec/support/webhook_helper.cr`) replaces it with a canned host → addresses mapping (unlisted hosts are unresolved). Any spec that exercises a resolution-dependent path — the B-76 authoring gate, the unresolvable-host cases — installs the fake: real lookups are environment-dependent (a wildcard-resolving resolver turns an NXDOMAIN case into a private-address rejection) and a cold negative lookup can cost seconds. One exception: the telemetry probe spec (`spec/telemetry/trace_guard_spec.cr`) resolves a `.invalid` host for real — RFC 6761 reserves the TLD, so the name never resolves, and the port-1 URL keeps the outcome the same under a wildcard-resolving resolver.
- All data tables are reset before each example by the global truncation. **Do not call `db_truncate_mutations` in local `before_each` hooks** — it's redundant.

- Environment-specific dotenv loading is done inline (no dependency) — `.env.template`-style.
- Mutation-to-projection trigger integration tests (`spec/mutation/mutations_spec.cr`) use raw SQL via a direct `PG` connection instead of the Crystal mutation API, since the trigger logic lives entirely in PL/pgSQL. Each test creates a fresh `doc_id` (ULID) to avoid cross-contamination — there is no per-example DB reset since migrations are stateful.
- When writing a spec that exercises a PL/pgSQL function, prefer the `db.query_one(...) do |rs|` block form with explicit `rs.read(Type)` calls rather than the `as:` shorthand, because the result set may contain nullable columns (e.g. `deleted_at timestamp`).
- Use `unique_suffix` (from `spec/support/db_helper.cr`) for short unique fixture names. It draws from the random portion of a ULID — the timestamp portion alone would collide under tight loops.
- Schema migration specs use `with_temp_doctype` to create a fresh doctype per test. They follow a pattern: create a v1 doctype → create a document → update the doctype to v2 with a migration script → read the document and verify the migration was applied.
- When testing `Doctype::Update`, use `db_truncate_mutations` between tests if they share a doctype. Prefer `with_temp_doctype` to avoid collisions entirely.
- The `$force` flag in doctype update tests is propagated via `$force: true` at the root of the request JSON body.
- The shared `spec/support/http_helper.cr` file builds the chain once into `HTTPTest` and all HTTP specs call `chain_handlers` once at the top level after route registration.
- **`make test` fails fast.** The target runs the spec binary with `--fail-fast` — the run aborts on the first failing example. Override with `make test FAIL_FAST=` to see the full failure list in one pass.

- **`make test` builds before it runs.** The target compiles the suite into `build/spec_run` and then runs that binary as a separate process, rather than using `crystal spec` (which compiles and tests in one process). The behaviour is the same; the reason is memory — Crystal's build allocates a large amount that it does not release, so an in-process build leaves that footprint resident for the whole suite. Building first lets the compiler exit and free it before any example runs. The build is skipped when no source changed, so a repeat `make test` goes straight to the run.
- **Top-level defs in spec files are program-wide.** When two files define the same name, the last one compiled silently wins — and `crystal spec` with no file arguments collects files in unsorted readdir order, so the winner differs between a fresh CI checkout and a dev tree. This once made a 2-scope RBAC fixture shadow the 3-scope one and fail only on CI. Rules:
  - A helper used by more than one spec file lives exactly once in `spec/support/` (loaded by `spec_helper.cr`, or required by the specs that need it). Never copy it into a spec file.
  - A helper owned by one spec file is declared `private def`. A `private def` at top level is file-scoped in Crystal — two files may both define the same private name without any cross-file effect.
  - `make spec_defs_check` (`scripts/check-spec-defs.sh`, a `backend-fast` CI step) fails when a def name is defined publicly in more than one spec file. Repeated defs inside one file are overloads and stay allowed.
- **No `def` inside a `describe`/`context` block.** The compiler rejects a `def` declared inside a spec block ("can't declare def dynamically"). Spec helpers sit at file top level: shared ones in `spec/support/`, file-owned ones as `private def` at top level (see the top-level-defs rule below).
- **`make test` passes a sorted file list.** The Makefile feeds `crystal spec` an explicit `find spec -name '*_spec.cr' | sort` list, so compile order is the same on every machine and every run. Do not run the suite with an unsorted glob when you need reproducible results.
- **5xx debug capture.** A request driven through `call_api` / `call_api_as` that answers 5xx gets its response body enriched with a `spec_debug` object — the request line, the exception class / message / backtrace / cause chain (when the exception reached Kemal's renderer), and the ERROR-level log lines emitted during the request. A spec failure message that prints the response body therefore carries the root cause; read `spec_debug` before adding tracepoint prints. Implemented in `spec/support/http_debug.cr` and `spec/support/log_capture.cr`; behaviour is pinned by `spec/http/http_debug_harness_spec.cr`. The suite stays quiet on the many deliberate 5xxes — set `SPEC_DEBUG_STDERR=1` to additionally echo each enriched body on STDERR behind a `spec-debug` marker.
- **RBAC enforcer diagnostics.** An enforcer assertion must name the denying layer, not a bare boolean. Use `expect_rbac_authorized` / `expect_rbac_denied` (`spec/support/rbac_helper.cr`) for `ReadEnforcer.authorized?` assertions — on an unexpected outcome they print the gate result, the matched and role-level permissions, the doctype definition's scopes, the row content, and the resolved `$self` comparison, pinpointing which layer denied.
- CLI subcommands print progress with `puts`. Wrap direct `CLI.run` calls in `silence_stdout` (from `spec/support/io_helper.cr`) so spec output stays clean. The redirect targets `STDOUT.fd` because the runtime duplicates fd 1 when stdout is a TTY.

## Debugging with incremental tracepoints

When a spec fails and the root cause is not obvious from the failure message, insert temporary `STDERR.puts` tracepoints at key pipeline stages rather than guessing. For 5xx failures, the harness already reports the exception and the captured error log (see Testing → 5xx debug capture) — add tracepoints only when that is not enough:

1. Identify the pipeline(s) involved (create, read, update, action, compute).
2. Add `STDERR.puts "TAG: #{value.inspect}"` at strategic points: after parsing input, after validation, after script execution, after compute, before persist.
3. Run the single failing spec (`crystal spec path/to/spec.cr:LINE`) to see exactly where the value diverges.
4. Remove all tracepoint lines once the root cause is found.

Crystal-specific notes for tracepoints:
- Use `STDERR.puts` (not `$stderr.puts`) — Crystal does not support `$` global variables.
- Crystal `Hash` iteration order is undefined (`Hash` is not insertion-ordered in Crystal), so when debugging field-level values, trace specific field names rather than relying on hash iteration order.
- Use `.inspect` on `JSON::Any` and `Lua::Engine::Value` to see both the type and the value (e.g. `JSON::Any(0)` vs `JSON::Any(9900)`).

## Quirks

### Database quirks

- Migrations use `-- UP` / `-- DOWN` markers. The migration runner (`Facet::Migrate`) reads SQL files, extracts the `-- UP` section, and applies pending ones tracked in a `_migrations` table.
- Database reset (`db_reset`) drops, recreates, and re-migrates the database. Used in tests and development.
- Mutation `arguments` use the JsonDiff format for `update` actions (`diff` for content, `meta_diff` for meta). `create` and `snapshot` use full content/meta instead.
- The `state` column on `projections` stores the ULID of the last mutation — it is NOT a status string.
- **`Audit::Rollback` to a `delete` mutation resurrects the document.** The snapshot trigger sets `deleted_at = NULL` when a snapshot is persisted after a delete. This is intentional — rollback goes back in time — but consumers should be aware that rolling back past a delete restores the document.
- **Tombstones keep `content`/`links`/`search` until pruned.** A delete tombstone retains its pre-delete payload so per-emit RBAC checks (e.g. WebSocket collection subscriptions) can scope-evaluate `deleted` events. `Cron::TombstoneContentPrune` clears the payload after the configured retention window — storage cleanup only. This is safe because `Audit::Rollback` replays from `mutations`, not from the projection row. The `periodic_snapshot` trigger skips tombstoned rows, the trigram search index is partial on `deleted_at IS NULL`, and every list filter targets `deleted_at IS NULL` — retained payloads never leak into lists, search, or snapshots. See [`mutation.md`](mutation.md#tombstone-content-retention).
- The `links` column on `projections` stores a precomputed JSON array of `urn:facet:…` URNs the document points to. Crystal precomputes it via `Document::Links.set_guc` and stores it through the `harness.mutation_links` GUC; the trigger only persists the array. See [`links.md`](links.md).
- The `version` column on `projections` is only modified by `snapshot` actions; incremental mutations (`create`, `update`, `delete`) do not touch it.
- **Never use `db.query(...) do |rs|` without calling `rs.move_next` or using `rs.each` first.** In `crystal-db` 0.14.0, `DB::Database#query` with a block yields the `ResultSet` **without** auto-positioning the cursor. Calling `rs.read(...)` on an unpositioned cursor hangs indefinitely. Always use `rs.each do` or `db.query_all(...)` to iterate. `query_one`/`query_one?` are safe — they call `move_next` internally.
- **`Database.with_transaction` uses PG savepoints for nesting.** The fiber-local, per-connection map `Fiber#txn_depths` tracks the nesting level (two pin slots can hold two connections on one fiber, and `with_transaction(db)` may receive a raw, unpinned connection). A nested `with_transaction` inside an existing transaction creates a `SAVEPOINT facet_txn_N` instead of `BEGIN`, and rolls back to the savepoint on error instead of aborting the outer transaction. Use `Database.with_transaction(db)` when the caller already holds a connection from an outer `with_db` or `with_transaction`.
- **An error return rolls the transaction back.** When a `with_transaction` block returns a value that includes the `Facet::ErrorResult` marker module (`Facet::ServiceError`, `Facet::ValidationError`, and every error type by convention), the wrapper rolls back and returns the error unchanged — a failed operation never keeps partial writes. A type that names a failed operation must include `Facet::ErrorResult` (the guard spec pins this). On the top-level rollback — the error-return path and the exception path alike — the wrapper also discards the buffered event queue (`Event::Publisher.discard`); a savepoint rollback leaves the decision to the outermost frame.
- **Connection modes: `ro` reads, `rw` writes.** Entry points name the mode: `Database.with_db(:read_only)` for read-shaped paths, `with_db` / `with_db(:read_write)` for writes. The resource label (domain id or `$tag`) is a second, optional argument; `*` routes to the default database entry. Services keep taking an explicit `db : DB::Connection` — only entry points request connections.
- **Pin reuse contract.** The fiber holds one pin per mode (`Fiber#db_ro` / `Fiber#db_rw`). An `rw` request reuses the rw pin; an `ro` request reuses the rw pin when present (read-your-writes), else the ro pin; otherwise the resolved route pool checks one out. A frame releases only a pin it checked out itself — the other slot stays pinned for the outer frame. A nested `with_db(:read_write)` inside a ro scope (the escalation pattern) therefore holds two connections for its duration.
- **Read-only enforcement.** Every ro pool runs `SET default_transaction_read_only = on` on each connection: a write mislabelled as a read fails loud with a PG error instead of silently succeeding. The lazy schema migration is the one sanctioned escape — the read path escalates to a nested rw block when it must write (see [`schema-migration.md`](schema-migration.md)).
- **Replica-lag contract (Q1).** Reads through a replica pool are eventual: a `GET` immediately after a `POST` may not see the new row yet. Every read surface accepts eventual consistency by decision; no sticky-read exception exists today. When one appears (e.g. token refresh → profile read), name it here and route that surface explicitly through the rw pin (`with_db(:read_only)` inside a rw scope reuses the rw pin — read-your-writes by the pin-reuse contract).
- **Secret data and volatile operational state live outside the doctype system.** Secret material goes through the `Secrets` store (see [`secrets.md`](secrets.md)) — it must never enter `mutations`, `projections.content`, or any document pipeline path. Volatile per-document operational state that is not a secret and carries no audit value (e.g. the TOTP replay guard) goes into `auth_state`. The same principle puts preference state in `account_settings` and derived side effects in `notifications`.
- **Secret payloads are self-describing.** The prefix before the first `.` names the algorithm (`gcm-v1.`, `sha256.`); `hash` payloads are native bcrypt strings starting with `$2`. Algorithms are never a schema, definition, or authoring concern — the stored `mode` column stays authoritative, and `Codec.parse_mode` is diagnostics only.
- **`hash` modes burn slow, `token` consumes before acting.** `Secrets.verify` on a missing slot runs a dummy bcrypt comparison (uniform timing); `Secrets.consume` is one atomic `DELETE … RETURNING` with the TTL in the same statement — zero rows means fail closed.
- **Rollback does not restore secret values.** `Audit::Rollback` replays content; secret slots stay current — old credentials must not resurrect. Markers in content replay like any other field.
- **Never log or email a secret value or a stage handle.** LoginEvent `details`, OpenTelemetry span attributes, and error messages carry field names and markers, never material.

### Time / Timezone

- **All tz-naive, all UTC.** Every timestamp column is declared `timestamp` (without time zone). The codebase stores UTC in every one of them; applications translate to a local timezone at read time. There are no `timestamptz` columns in storage.
- **The PG session `TimeZone` is pinned to UTC through a connection hook.** `Database.init` registers `SET TimeZone = 'UTC'` as the first hook on every pool, so `now()` casts to `timestamp` and `text::timestamp` interpretations are always UTC regardless of server/role defaults. The pin never travels through the libpq `options` URL parameter: **crystal-pg 0.30's `ConnInfo` parser silently drops it** (only host/port/db/user/password/ssl*/application_name/replication are read), so URL-embedded `-c key=value` pairs never reach the backend. `SET` after connect is the only path that lands.
- **The server process carries a global `statement_timeout`.** When `config.{env}.yml` declares `database.statement_timeout_ms`, `Database.init` registers a `setup_connection` hook that runs `SET statement_timeout = N` on every pooled connection — existing and lazily created. CLI entry points (`migrate`, `db_reset`, export/import, reproject) call `init` without the knob, so long migration DDL and reproject workers cannot be cancelled. The knob is optional: an absent `database:` section or key leaves the PG default (no timeout). Aggregate requests surface a cancellation as HTTP 503 — see [`http-layer.md`](http-layer.md) → Aggregate responses (sum).
- **`now()` defaults are safe.** With the UTC pin, `DEFAULT now()` casts the instant to UTC before storing it in a `timestamp` column — no migration change needed.
- **Doctype `datetime` and `period` field values are normalized to UTC before persistence.** `DatetimeType#normalize` and `PeriodType#normalize` (invoked via `Document::Normalize` in both `Document::Create` and `Document::Update`) accept ISO-8601 strings with timezone offsets (e.g. `2025-01-15T10:30:00+02:00`) and re-serialize them as UTC RFC-3339 (`2025-01-15T08:30:00Z`). The same canonical form is what every caller should compare and emit.
- **Crystal `Time.parse_iso8601` rejects tz-naive datetime strings** (`"2025-01-15T10:30:00"` raises `Time::Format::Error`) and **date-only strings** (`"2025-01-15"` raises too). Every accepted `datetime`/`period` input therefore carries an explicit offset, and `to_utc` is a lossless conversion. Don’t bypass normalization with raw string manipulation. Clients that send a date-only value to a timestamp filter get a no-match (`FALSE`) clause — a date is not a valid filter input for a timestamp target.
- **Query filters accept timezone offsets and normalize to UTC before binding.** This applies to:
  - `created_at` / `updated_at` filters on `assistant.Conversation` (`src/assistant/conversation.cr`).
  - `emitted_at` filters on `Audit::List` (`src/audit/list.cr`).
  - `datetime` field scalar filters (`eq`, `gt`, `gte`, `lt`, `lte`, `between`) on `Document::List` — stored values are tz-naive UTC text, so the query side is normalized to the same form before text comparison.
  - `created_at` / `updated_at` filters on `Document::List` — these do **not** route through `FilterSet` (whose LHS is `content->>'field'`); they target the `projections` columns directly via `Document::List#build_system_clauses` and cast the bound value to `::timestamp` (not `::timestamptz`) so the comparison stays tz-naive-to-tz-naive.
  - The same doctype's system-managed timestamp columns (`created_at`/`updated_at`) on `Document::List` — the latter route through a dedicated WHERE branch that targets the `projections` columns directly.
- **`period` / `dateperiod` range filters are already tz-aware.** `Document::List` casts the bound value to `tstzrange(... ::timestamptz, ...)` via the IMMUTABLE wrappers in migration `0002_indexing.sql`, which honor offsets natively. No further normalization is needed there.
- **Helper:** `Util::TimeHelper.to_utc_rfc3339(value : String) : String?` is the single utility for ISO-8601 → UTC RFC-3339 normalization. Returns `nil` on parse failure so callers can degrade to a no-match clause rather than 500-ing. Do not parse ISO-8601 datetimes inline in services — use this helper.
- **The process pins `TZ=UTC` at boot.** `src/main.cr` and `spec/spec_helper.cr` set `ENV["TZ"] = "UTC"` before anything loads, so an accidental `Time.local` resolves to UTC instead of the host zone. The codebase uses `Time.utc` everywhere; the pin turns a lapse into a no-op instead of a machine-dependent skew.
- **The application role's default session timezone is UTC.** Migration `0001_document_store.sql` runs `ALTER ROLE CURRENT_USER SET timezone TO 'UTC'`, so clients that connect with the application role (`psql`, BI tools, one-off scripts) start with a UTC session even without the libpq `options` pin. A client using a **different role** must set `TimeZone=UTC` itself — see [migrations.md](migrations.md) → Deployment constraints.
- **Binding a non-UTC `Time` into a naive column silently skews it.** crystal-pg serializes `Time` parameters as RFC-3339 with the value's own location offset (`lib/pg/src/pq/param.cr`), and casting offset-bearing text to `timestamp` **discards the offset** (wall clock kept, instant lost): `'2025-01-15T10:30:00+02:00'::timestamp` stores `10:30:00`, not `08:30:00`. Only `Time.utc` values may be bound; string filters normalize through `Util::TimeHelper.to_utc_rfc3339` before binding.
- **One serializer leaves the API.** `Time#to_rfc3339` converts to UTC by default and emits the `Z` form, and crystal-pg reads naive `timestamp` columns into UTC-located `Time` values (`TimeDecoder` adds microseconds to `Time.utc(2000, 1, 1)`), so round trips are lossless. Never read a timestamp column as `String` (PG's text form has a space separator and no `Z`), and never call `.to_local` / `.in(...)` before serializing.

### Doctype system quirks

- Two validation services exist: `Doctype::Validation` (schema-level) and `Document::Validation` (document-level). They are separate concerns — don't merge them.
- Reserved action names (`validate`, `create`, `update`, `delete`, `migrate`, `snapshot`, `history`, `rollback`) are forbidden in doctype definitions. The canonical list lives on `DoctypeDefinition::RESERVED_ACTIONS` and is referenced by `Doctype::Validation`.
- `FieldType::Data` fields are computed (Lua-driven) and must **not** be user-writable. The validation service rejects them from input.
- `Reference` fields use the qualified `domain.Doctype` target form (e.g. `"identity.Person"`). A bare name is refused at authoring time (F02-01) — it is never expanded to the owning domain. The `domain` field is no longer used.
- `A **`migrations`** field on `DoctypeDefinition` maps version numbers to Lua function names. Every version gap from current to target must have an entry. The validation service checks this via `validate(definition, current_version)`.
- `Doctype::Update` supports two modes: **same-version** edits (non-breaking: field additions, metadata changes, script fixes) and **version bump** (+1: breaking changes with migration functions). Same-version edits reject every non-additive data-shape change (field removal, type change, nested sub-schema edits, `collection` flips, constraints, enum key removal, reference surface, `children`, `member_of`) unless `$force: true` is passed in the JSON body — see [doctype-system.md](doctype-system.md) → Version gate.
- **The stored `migrations` map survives a PUT (B-301).** The same-version guard forces the body to omit `migrations`, so `Doctype::Update` merges the stored map into the effective definition after the guards (body keys win, stored entries survive, `$force` skips the merge). A definition with `migrations` and no `script` is rejected — a migration function runs only through the Lua script. Recovery for a sticky `meta.migration_error` marker: `facet doctype:migrate-retry <qualified_doctype>` — see [schema-migration.md](schema-migration.md) → Error recovery.
- **Composition is mutual** — a `children:` entry on the parent and `member_of` on the child, always together. `aggregate_root: true` with `member_of` is a hard validation error; a one-sided edge fails publish/import with `422` and is flagged by `Doctype::Check` on live domains. See [doctype-system.md](doctype-system.md) → Composition.
- **Crystal's YAML parser follows YAML 1.1** — bare words `on`, `off`, `yes`, `no` are parsed as booleans, not strings. When used as hash keys they are stored as `Bool`, not `String`, and silently collide (`on` and `yes` both become `true`). `YamlHelper.to_json_any` raises `ArgumentError` on any non-String hash key to fail loud. Quote keys that collide with YAML 1.1 reserved words: `"on": value` instead of `on: value`.
- **Sequential identifiers use `pg_advisory_xact_lock`** to serialise creates per doctype. The lock key is `hash("seq:#{domain}:#{doctype}")`. On overflow of all digit groups the system falls back to a ULID — the document is never rejected due to counter exhaustion. See [`doc/backend/util-sequence.md`](util-sequence.md) and the [Sequential identifiers section in doctype-system.md](doctype-system.md#sequential-identifiers).
- **`normalize` must be null-safe.** `Document::Normalize` (and the `object`/`array`/`dictionary` recursions) hand each value — nulls included — to the field type's `normalize`; the array and dictionary recursions null-skip explicitly, and `ObjectType#normalize` does too. A type whose `normalize` dereferences the value (`value.as_s`, …) crashes on any explicit-null field — e.g. a seeded all-null document (`core.SystemSettings`). New field types: either keep the default identity `normalize`, or guard with `as_s?`-style accessors.
- **Crystal class variables resolve against `self.class` inside instance methods.** A bare `@@var` read in an instance method of a SUBCLASS sees the subclass's own (never-written) storage, not the base's — a base-class `def self.configure!` can write `@@var` while every subclass instance reads `nil`. Access shared memo state only through explicit class methods (`BaseEmail.memo_mail_view`), or through the class name where the variable lives. This bit `BaseEmail#from` the first time it read `@@mail_view` from an instance method.

### Qualified reference storage contract

- **Every `reference`-typed field value is stored fully qualified as `{domain}.{Doctype}.{id}`** (e.g. `"iam.Account.acc_alice"`, `"crm.PipelineStage.06FWD..."`). The `ReferenceType#validate` rejects bare values or values whose `{domain}.{Doctype}` prefix does not match the field's declared `doctype:`. `ReferenceType#normalize` qualifies bare ids before validation and persistence so API callers may still send bare ULIDs.
- **The id segment may itself contain `.`** — split only on the first two dots. `ReferenceType#split_qualified` (and `DocURI.parse_dotted`) implement this; never split the whole string on `.`.
- **`projections.id` is the opaque id only.** A reference *value* (`{domain}.{Doctype}.{id}`) is never equal to `projections.id` for `Document::Create`-authored docs (whose id is a bare ULID). The exceptions are the **named-id doctypes** and **imported fixtures**. Named ids: `iam.Roles` rows are pinned to `iam.Roles.{name}` and `iam.Account` rows to the **lowercased email address** (both derived in `Document::Create.resolve_doc_id`; a conflict answers `NamedIdError` 409 — for accounts that is the application-level email-uniqueness check, and the account's `email` content field always equals its id because the create hook lowercases it). The email id makes every raw surface readable: `mutations.actioner_id` names the actor, CSV exports of account references carry `iam.Account.jane@corp.com`, and the account's own API path is `/Api/iam/Account/jane@corp.com`. Account emails are **immutable** — a doctype-keyed gate in `Document::Update` refuses a change (a case-only rewrite passes; it is a re-save, not a rename). Fixtures: `Domain::Portable::Import.create_document` passes the bundle's filename-stem id verbatim as `doc_id:` to `Mutation::Client.create`, so a fixture row whose bundle file is named `crm.Company.1.yml` literally has `projections.id = 'crm.Company.1'`. Resolution code that walks from a reference value to a projection row must therefore try the qualified form first, then fall back to the prefix-stripped opaque id (see `Document::DisplayName::DatabaseReferenceResolver#resolve` and `Document::ReferenceCheck.strip_qualified_id`).
- **`Document::Normalize` runs before `Document::Validation`** in `Document::Create` (content path) and **`Document::Normalize.action_args` runs before `validate_action_args`** in `Document::Action` (action-args path). The strict-format `ReferenceType#validate` would otherwise reject bare-id callers; normalization qualifies them first.
- **`$self` in a RBAC named-scope `where` matches both stored principal forms**: the bare account id (what a plain `string` field holds — the `ctx.root.owner_id = ctx.actor.id` create-hook recipe) and the qualified `iam.Account.<id>` reference form (what a `reference → iam.Account` field stores). `RBAC.principal_forms(account_id)` returns the pair. `ScopeMatcher.match?` (single-doc read / write enforcement) compares the stored value against both forms; `ScopePredicateSql.build_clauses` — the single SQL compiler for the list path, query-time `?scope=` filters, and `ContextResolver` context-set resolution — emits an OR over both forms for `eq` and pattern operators, and an `IS DISTINCT FROM` pair for `ne`. A stored value that equals neither form does not match.
- **The HTTP layer resolves id shapes once**: `HTTP::Helpers.canonical_doc_id` canonicalizes the `:id` of every document route (flat and nested root) — exact match wins, then the `{domain}.{Doctype}.` prefix is stripped and the bare id is tried. Frontend consumers (`Capsule`, `ReferencePicker`, `DocumentCard`) therefore issue a single `show()` for either shape. `ReferencePicker.createDriverSearch` emits the qualified form (`${qualifiedDoctype}.${item.meta.id}`) as the form value, since the API only returns the bare `projections.id` in `meta.id`.

### HTTP quirks

- List requests support both JSON body and query-string formats. Query-string parsing uses `filters[key]=value` style; sort uses comma-separated fields with optional `-` prefix.
- The list surfaces also serve `QUERY` (RFC 10008): a safe, cacheable GET whose parameters ride a JSON body. QUERY rejects query-string parameters with `422`; GET keeps the body + query-string merge. See [`doc/backend/http-layer.md`](http-layer.md) → QUERY method.
- All CRUD routes are implemented and wired: create, read, update, delete, list, nested resources, and action execution. See [`doc/backend/http-layer.md`](http-layer.md) for the full route table.
- The `GET /Api/:domain/:doctype/:doctype_id` response includes an `X-Document-Migrated` header set to `true` if lazy schema migration was applied during the read.
- `PUT /Api/core/DocType/:doctype_id` accepts an optional `$force: true` at the root of the JSON body to bypass same-version guards (every non-additive data-shape change — see [doctype-system.md](doctype-system.md) → Version gate).

### JSON::Any quirks

- A `JSON::Any` value is a wrapper — `value.is_a?(Array)` (or any raw-type
  `is_a?` check) is always false, and the compiler cannot catch it. Test the
  wrapped value with the wrapper's nilable accessors instead: `as_a?`, `as_s?`,
  `as_h?`, and so on. This exact trap silently broke every WebSocket subscribe
  frame once (`handle_frame` tested `args_raw.is_a?(Array)`), so treat any new
  `JSON::Any#is_a?` as a bug.
- The raising accessors do not raise JSON errors: `as_h` / `as_bool` / `as_s`
  / `as_i` raise `TypeCastError`, and `[]?` on a non-object raises a bare
  `RuntimeError`. Neither is a `JSON::Error`, so a `rescue JSON::ParseException`
  (the standard 422 channel) does not catch them — the request surfaces as a
  500. Use the nilable accessor plus an explicit raise naming the key and the
  got-type (see `DoctypeDefinition.json_kind`, `Doctype::DefinitionError`).
- Crystal truthiness turns `false` falsey — `value.as_bool? || raise` and
  `unless flag = value.as_bool?` both fire on a legitimate `false`. Assign
  first, then test `if flag.nil?` explicitly.

### Lua engine quirks

- `Engine::Value` normalization: tables with consecutive 1-indexed integer keys become `Array`; all other tables become `Hash(String, Value)`. Functions are preserved as `::Lua::Function`.
- Standard libraries (`string`, `math`, `table`, `utf8`) are loaded by default. The `os`, `io`, `debug`, `package`, and `coroutine` libraries are **not** loaded (see [Lua Engine → Sandboxing](lua-engine.md#sandboxing)).
- Errors wrap `Lua::LuaError` as `Engine::Error < ::RuntimeError`, accessible via `.lua_error`.
- Doctype scripts must use the **module pattern**: `local export = {}; ...; return export`. Functions are defined as `export.create(ctx)`, `export.promote(ctx, args)`, etc.
- Lifecycle hooks (`create`, `update`, `delete`) are **optional** — if absent from the export table, no Lua code runs for that lifecycle event.
- Named actions (from `definition.actions`) are **required** — `ScriptValidator` rejects a doctype definition if a declared action function is missing from the export table.
- Computed fields (`type: data`) are also **required** — `ScriptValidator` checks that for every `Data` field with a `compute` value, a corresponding `compute_{suffix}` function exists in the export table.
- Computed fields are evaluated at runtime after create (all fields) and after actions (only fields whose `compute_when` intersects the changed fields). `Document::Compute` spins up a single Lua engine per batch, updating `ctx.root` between fields so subsequent computations see the latest state. **The function must return the value** — the return value is what lands in the field; a `ctx.root` write to the field is honoured only when it differs from the pre-call value, and a nil return with no write clears the field.
- A `Facet::ServiceError` raised through the `document.*` Lua helpers keeps its native HTTP status: when the script does not recover through `pcall`, the driving service (named action, create/update/delete hook) answers with the recorded status (flat-create guard → 422, missing update target → 404) instead of an opaque 500. A script bug with no recorded refusal answers **422** with the Lua error message (`Script error: <lua message>`) — never a bare 500.
- Migration functions (from `definition.migrations`) are **required** when the schema version is bumped — `ScriptValidator` checks that every declared migration function exists in the export table. Like all doctype functions, they must be inside the module's export table (e.g. `function export.migrate_from_1(ctx)`) — bare top-level `function migrate_from_1(ctx)` will not be found in `_MODULE` and will fail validation.
- The `ctx` table passed to every function provides `ctx.root` (document content, mutable), `ctx.error(msg)` (validation error collector), `ctx.actor_id` (string), and `ctx.now` (ISO 8601 timestamp string). Migration functions receive the same `ctx` table with `actor_id` set to `"system:migration"`. The `create`/`update`/`delete` hooks and named `action` functions additionally receive `ctx.actor` — a read-only RBAC surface (identity, role, the permission scope alias for this action, resolved context sets) so the script can enforce row-content rules RBAC cannot express. Migration contexts do not. See [`lua-engine.md` → ctx.actor](lua-engine.md#ctxactor).
- For the `create` lifecycle hook, mutations to `ctx.root` are persisted as the final document content — the script can set defaults, generate slugs, etc.
- For the `update` lifecycle hook and `action` functions, mutations to `ctx.root` are diffed against the original and persisted as an `update` mutation.
- Migration functions run at read time when the document's `meta.schema_version` is less than the doctype's current version. The result is persisted as a `snapshot` mutation, making subsequent reads skip migration.

### Index management quirks

- The `doctype_indexes` table tracks PostgreSQL partial indexes on `projections`. Each row has a status (`pending`, `active`, `error`, `dropped`) — never query `pg_indexes` directly to determine if an index is managed.
- `CREATE INDEX CONCURRENTLY` and `DROP INDEX CONCURRENTLY` run in background fibers outside any transaction. The doctype mutation always succeeds regardless of index creation outcome. Every DDL unit holds the **DDL gate** (`Index::Manager.with_ddl_gate` — a session-level PG advisory lock taken by non-blocking `pg_try_advisory_lock` polling) so two CONCURRENTLY statements never overlap on `projections`; without it they deadlock (40P01) whenever a domain copy/publish or two concurrent doctype edits schedule DDL at once. The polling form is mandatory: a session blocked on `pg_advisory_lock` holds an open implicit transaction that the gate-holder's CIC snapshot-wait locks onto (the B-46 deadlock — the queued fiber got killed and its row stayed `pending` behind a 200). A try-lock poll never blocks, so no session ever waits on the gate. DML writers never wait on the gate.
- Index creation failures leave the tracking row in `error` status with the error message stored — a failure while acquiring the DDL gate itself marks the row `error` the same way. The row is **not** automatically retried on the next `sync` — a subsequent `sync` call (on next doctype update) sees `error` rows as already-existing in `fetch_current` and does **not** retry them. PG deadlock (40P01) is retried in place with backoff (3 attempts runtime, 5 in the CLI) before a row settles into `error`; between CREATE attempts the half-built leftover index is dropped first, or `IF NOT EXISTS` would silently keep an INVALID index. To recover, use the `index:retry` CLI command — it retries `error` rows and `pending` rows stale beyond 10 minutes (casualties of a DDL fiber that died mid-batch), removes any leftover inside the gate before rebuilding, initialises its own pool, and exits non-zero when a row still fails.
- The `UNIQUE` constraint on `(domain, doc_type, field_name, index_type)` prevents duplicate index records. Race conditions between concurrent syncs are handled by `ON CONFLICT DO NOTHING` during insert.
- When seeding core doctypes, `Index::Manager.sync` is only called for documents that successfully parse as `DoctypeDefinition`. The `core.Domain` definition uses `"type": "any"` in the grants fields which is not a registered field type — index sync is gracefully skipped with a `rescue ArgumentError`.
- **Range indexes (`gist_tstzrange` / `gist_daterange`)** for `period` / `dateperiod` fields use IMMUTABLE wrapper functions (`facet_tstzrange` / `facet_daterange` from migration `0002_indexing.sql`). PostgreSQL marks `text::tystamptz` and `text::date` as STABLE not IMMUTABLE, so the wrappers are required for `CREATE INDEX ... USING gist (...)` expressions over JSONB extracts. The IMMUTABLE marking truthfully reflects the runtime contract: doctype validation rejects any input that is not a well-formed ISO-8601 UTC string. **If you ever loosen the validation to accept non-ISO formats, the wrappers' IMMUTABLE marking must be revisited.**
- **Range query operator expansion lives at `Document::List`, not in `FilterSet`.** `FilterSet` is deliberately schema-agnostic by contract; the range operators (`__contains`, `__overlaps`, `__within`) require knowledge of the field's PG range type (`tstzrange` vs `daterange`), which `Document::List` looks up against the doctype definition. The LHS in the WHERE clause must use the IMMUTABLE wrapper (`facet_tstzrange(content#>>'{f,start}', content#>>'{f,end}')`) rather than the raw `tstzrange(...)` constructor — PostgreSQL's planner matches on the parsed expression tree, so using the raw constructor would NOT use the GiST index.
- **`between` is rejected on `period` / `dateperiod` fields.** Its scalar-between semantics (`field BETWEEN a AND b` → `<@`) are misleading when the field is itself a range. Use `within` directly. This is enforced by both `PeriodType.validate_definition` / `DatePeriodType.validate_definition` and the cross-cutting `validate_field_operators` check in `Doctype::Validation`.
- **Range operators (`contains`, `overlaps`, `within`) are rejected on non-range field types.** Enforced by `validate_field_operators` in `Doctype::Validation` — they have no indexable semantics on scalar, container, or reference fields.
- **`currency` operator is rejected on non-`money` field types.** Enforced by `validate_field_operators` in `Doctype::Validation` — money-specific text equality on the stored ticker.
- **Money indexes (`btree_money` + `btree_money_currency`)** for `money` fields use the IMMUTABLE wrapper `facet_money_value_as_numeric(content->'field')` from migration `0002_indexing.sql`. The wrapper reads the object's `value` member (must be a JSON string matching the decimal regex `^-?[[:digit:]]+([.][[:digit:]]+)?$`) and casts to `numeric` — returns `NULL` for any other shape so a directly-mutated malformed row degrades instead of raising. The IMMUTABLE marking truthfully reflects the runtime contract (mirror of the `facet_tstzrange` rule above): `MoneyType#validate` only accepts well-formed decimal strings, so the cast result is deterministic. The regex guard is belt-and-braces for the bypass path. **If `MoneyType#validate` ever loosens to accept non-decimal `value` strings, the IMMUTABLE marking stays sound because the regex guard rejects them, but revisit the guard if the accepted grammar widens past the regex.**
- **Money filter operator expansion lives at `Util::FilterClauses.money_clauses`, not in `FilterSet`.** `FilterSet` is schema-agnostic and only knows `content->>'field'` text extracts; money filters route through `facet_money_value_as_numeric(content->'field')` for value comparisons and `content#>>'{field,currency}'` for `__currency`. The filter value grammar accepts `"<CCY> <amount>"` (currency-prefixed) or `"<amount>"` (currency-agnostic); unknown ccy or malformed amount raises `List::MoneyFilterError` which `List.call` surfaces as a 422. The same builder also serves the RBAC scope-predicate compiler (`ScopePredicateSql`).
- **Index names are embedded unquoted in DDL SQL, so the domain slug is sanitised to lowercase `[a-z0-9_]`.** `Index::Naming.index_name` derives the slug from the domain string: any character outside the PostgreSQL unquoted-identifier grammar (`-`, `.`, uppercase, …) is replaced with `_`, and the string is lowercased. The SHA-256 suffix still disambiguates domains whose slugs collide (e.g. `new-crm` vs `new.crm`) because the hash input retains the original, unsanitised domain. Do not bypass `index_name` and embed a raw domain into a `CREATE INDEX` / `DROP INDEX` statement — the unquoted identifier would either syntax-error or be silently fold to lowercase and mismatch the `doctype_indexes.index_name` column.

### RBAC quirks

- **One active role per request, roles never merge.** The effective permission set is exactly one role's map, verbatim. Cross-role scope reconciliation is deliberately absent — it has no non-surprising answer.
- **No `account_active_roles` table.** The active role is request-supplied (header in dev, JWT claim in production), global, never per-domain.
- **No `doctype_sensitivity_tags` table.** Tags are free strings on `FieldDefinition#tags`; the valid set is derived at authoring time.
- **No `additional_properties` field-type feature.** `context_sets` follows the same free-form + custom-validator pattern as `core.Domain.grants`.
- **Roles cannot author custom query predicates.** A permission's `scope` field is either absent, `$all`, or `$<named_scope>` where `<named_scope>` is a named scope declared on the target doctype. `$self` and `$<context_set>` references exist *inside* a named scope's `where`, never directly on the permission.
- **`visible_tags` defaults to `["default"]` (fail-closed).** A role with no explicit value sees only untagged fields. Only `["*"]` emits all fields.
- **Trusted-bypass tier:** `ContextResolver`, `AccountLoader`, raw `Client.fetch_projection`/`fetch_content`, and `actioner_id == "system"` bypass RBAC by design.
- **Context sets are domain-owned** (stored on `core.Domain.definition.content.context_sets`), never global, never on the role. A context set may only `from:` a DocType in the same domain.
- **Named scopes are doctype-owned** (stored on `{domain}.{Doctype}.definition.content.scopes`), declared by whoever defines the doctype. A named scope's `where` may reference `$self`, a literal, or `$<context_set>` declared in the same domain; field names must exist on the doctype, or be the reserved `$parent_id` token (reads `meta->>'parent_id'`).
- **Scope validation at authoring time is a hard error** — `validate_permissions` rejects unknown-scope-alias role permissions; `validate_named_scopes` rejects named scopes with unknown fields, unknown `$<context_set>` references, or out-of-domain context set usage. `validate_context_set_definitions` rejects acyclic-violating context sets and SQL-unsafe field names in `select`/`where`. All wired into the role / domain / doctype create/update paths.
- **Named-scope alias expansion happens at enforcement time, never persisted.** `Permission#to_h` preserves the alias verbatim. Redefining a named scope's `where` propagates to all roles that reference it on the next enforcement (see `ScopeExpander`).
- **`create` permissions consult `scope` only as a permission-presence check.** Named scopes apply to *existing* rows; at create time the row doesn't exist yet. Row-content rules on create belong to Lua `create(ctx)` lifecycle hooks (where the script can `ctx.error(msg)` to reject bad rows). `update`/`delete`/`action` enforce the named scope's `where` against the existing projection. **Each of these checks its own action name** — a `delete` requires a `delete` permission, not `update`; a named action requires a permission matching the action name. They are NOT collapsed under `update`.
- **`ctx.actor` is exposed to every lifecycle hook and named action.** `Create`, `Update`, `Delete`, and `Action` contexts all receive `ctx.actor` (identity, role, visible_tags, the *action's own* permission scope alias, and resolved context sets) so a script can branch on the caller's scope. `Migrate` does not. See `doc/backend/lua-engine.md` → ctx.actor.
- **Permission `on` path uses domain isolation** — `*.*` is the sole deliberate exception (admin role). All other permissions have an explicit domain.
- **Scope validation at doctype authoring time is a hard error.** A doctype create/update rejects a named scope that references an unknown field or an undeclared context set.
- **`FieldDefinition#tags` is the sensitivity-tag mechanism** — free-form strings; absent resolves to `["default"]`. Two consumers: RBAC field visibility (below) and cross-domain grants (see [`domain-grants.md`](domain-grants.md)).
- **`select` is a Crystal keyword** — the `ContextSet` struct uses `select_field` for its getter name. The JSON field name in the domain definition is still `select`.
- **IAM writes carry one authority boundary.** Every caller-controlled write on `iam.Account` / `iam.Roles` — create, update, delete, named action, rollback — runs through `RBAC::RoleAuthority.authorize_transition` after structural validation and before persistence. The elected active role is the caller authority (roles never merge); the caller level comes from its role's required `level` field (0–100); a missing or malformed level denies the Real write (fail closed). Target protection blocks writes to accounts or roles above the caller's level; role authoring constrains the resulting permissions, tags, and assistant power to the union of the previous role's power and the caller's own. System alone bypasses it. See [`rbac.md`](rbac.md) → Role authority.
- **Invisible fields are refused on the write plane.** `WriteEnforcer.authorize_field_writes` refuses caller-submitted writes into fields the caller cannot see (an explicit `null` included) on create and update; `authorize_field_changes` refuses named-action final diffs and rollback transitions that land inside invisible fields, compared on the actual before/after states. Trusted lifecycle work (defaults, compute, replication, hooks) stays outside the guards. Masking lives at presentation boundaries only (`Document::Presenter`); mutation services return raw projections.
- **Audit history redacts by shape.** `Audit::List` removes invisible field values from mutation arguments and lists the removed content paths in the `redacted` wire field (arrays of path segments). Missing definitions and unknown historical fields fail closed (all values removed); System, Preview, and wildcard-tag roles get raw arguments with `redacted: []`. See [`audit.md`](audit.md) → Argument redaction.
- **Unexpected 500 bodies stay generic.** `JsonErrorHandler` answers `"Internal server error"` for every unexpected exception, `PQ::PQError` included; the class, message, and backtrace go to the `facet.http` log. The one expected case — the mutation-log concurrent-write race — keeps its 409 body. See [`http-layer.md`](http-layer.md).
- **An app-owned API key 401s opaquely when the service role misses a required grant action.** The body names nothing (anti-enumeration); the WARN log names the gap (`GrantResolver.missing_required_actions` — e.g. `update on fin.Invoice`). Grant `write` expands to required `create` + `update`, so a role line `create` alone does not satisfy it. See [`app-system.md`](app-system.md) → Diagnosis: every route 401s with a valid key.

### Webhook quirks

- **Webhook RBAC is checked at enqueue time, not execute time.** `Webhook::AuthCheck` runs the six-step gate on the event-stream fiber, before a `webhook_delivery` row is written. The execute-time `Webhook::Dispatcher` does no RBAC and no projection reads — the whole `url` / `secret` / `headers` set rides in the job payload. This is the reverse of the HTTP layer's request-time enforcement; a binding revoked after enqueue still delivers (the row was already authorized), and the next source mutation is the earliest point the revocation takes effect.
- **Replay shares the enqueue gate.** `POST .../replay` calls `Webhook::AuthCheck` — the exact code path `Webhook::Handler` uses. Do not duplicate the check; a drift would let replay deliver on a binding the handler would have skipped.
- **The signing secret is per-webhook, never config-level.** The `secret` field on the `core.Webhook` projection (server-generated ULID, immutable after create) signs every body. The secret lives only in the `background_jobs` payload — the `webhook_calls` log rows never hold it, so log views echo nothing to strip.
- **`background_jobs` and `webhook_calls` are not in the global truncation list.** Every spec that creates their rows must delete them in `before_each` (see `spec/support/webhook_helper.cr`).
- **Eight job lifecycle events are opt-in, and the gate swaps targets.** `export_completed` / `export_failed` / `import_completed` / `import_failed` (documents) and `domain_export_completed` / `domain_export_failed` / `domain_import_completed` / `domain_import_failed` (portable domains) fire only for bindings whose `events` list names them (`Event.opt_in_event?` — the same rule `notified` follows); a match-all webhook never receives them. Their subject is a `background_jobs` row, not a projection, so `AuthCheck` step 6 swaps to the source doctype's own `core.DocType` projection — a role hears about finished jobs when it can read that definition row: an explicit `read core.DocType` line, or any read/create/update/delete line on the source doctype itself (the metadata gate, B-86).

### Import/export quirks

- **`lease_ttl_s` is a per-row override, and long jobs must set it.** `Jobs::Queries.insert` accepts `lease_ttl_s` (nil means the worker's TTL at claim); `claim` computes `locked_until` from the row's own value when set. The import/export jobs enqueue with `jobs.long_lease_ttl_s` (default 1 h) because any import or export outlives the 60 s worker default — the sweep is the only crash detector, and a finite lease is what turns a dead worker's row into a clean re-execution instead of a zombie. See [`jobs.md`](jobs.md), Per-row lease override.
- **Job artifacts carry account provenance and prune like any unreferenced row.** The export file and the import's staged file + manifest get an `_account` owner row for the requesting account (`ImportExport::Artifacts.put`); a system requester stays ownerless. The requester can download through the artifact gateway, but retention is still the dangling-sweep grace window (`artifact.prune_after_days`) — account-scoped owner rows never resolve against `projections`, so the eligibility query is unchanged. The download route answers `404` for a pruned artifact.
- **Bundled doctype definitions pass the authoring battery before persist (B-302).** The fresh-import create and the merge path's missing-row create run `Doctype::Validation.validate`, `ScriptValidator.validate`, `DraftTargetCheck`, and named-scope validation; the merge path's version gate runs the same checks plus the version rules. A definition the REST authoring door would refuse rejects the import with a `422` and the transaction rolls back. See [`portable-domains.md`](portable-domains.md) → Authoring gate on bundled definitions.
- **Bulk import rows act as `actioner_id: "import"`.** `Document::Import` runs every row through the full create/update path with that constant actor — audit rows and Lua hooks (`ctx.actor_id`) can tell a bulk import from a hand edit. The completion event carries the requesting account id, not `"import"` — it describes the job, not the rows.
- **Export reads storage as-is and skips lazy migration.** The export service runs plain SELECTs in a `REPEATABLE READ, READ ONLY` transaction: zero document events, `mutations` untouched, no Lua migration of stale rows. A row untouched since the last `schema_version` bump exports in its stored, pre-migration form — JSON rows carry `meta.schema_version` so staleness is visible. A download must never be a writer.
- **A failed transaction's buffered events must be discarded on a worker fiber.** `Event::Publisher.enqueue` buffers per fiber, and an HTTP request fiber simply dies on error — but a `Jobs::Worker` fiber is long-lived. A service that rolls back inside a job (the import's first-failing-row abort) calls `Event::Publisher.discard` before it returns, or the rolled-back rows' events ride the next flush.
- **Domain-level bundles ride the same plumbing.** The portable-domain concern (`domain_export` / `domain_import` jobs) reuses `ImportExport::Artifacts`, `CallerContext`, and `JobOutcome`, gated on the `core.Domain` document (read for export, create/update for import) and definition-only over HTTP. See [`portable-domains.md`](portable-domains.md) → HTTP + jobs.

### File-tool quirks (scratch work outside the tracked tree)

- **The editor file tools see only indexed paths.** A directory that a terminal command creates under a gitignored path (for example `tmp/new-scratch/`) stays unindexed: `read_file`, `edit_file`, `write_file`, and `find_path` answer "not in the project", although the files exist. A file directly in an already-indexed directory (for example `tmp/foo.cr`) is indexed and fine. This mixed behaviour is easy to misread as a missing file.
- **For scratch copies of other repos (for example agent-cr), use a non-gitignored directory at the repo root** — for example `agent-cr-fix/`. Untracked but unignored directories are indexed normally, so the file tools work on them. Delete the directory when the work is done.
- **Terminal commands are the fallback with no indexing limit.** They read and write any absolute path (for example `cat /abs/agent.cr/src/x.cr`), and `git -C <path>` works from the repo cwd. Only `create_directory` and the `cd` parameter stay limited to project paths. The pattern for upstream fixes: `cp -r` the foreign repo into an unignored scratch dir, edit and run its suite there with the file tools, then `cp` the changed files back and commit with `git -C`.
