# App System

`app.App` is a seeded core doctype that registers an external application which uses Facet as its data and identity source. An App never runs inside the Facet process and never touches the database directly. The registration schema (Phase 1), the grant resolution engine (Phase 2), the Layer-1 enforcement at the service layer (Phase 3), the OAuth authorization-code flow (Phase 4), refresh/rotation/revocation (Phase 5), and audit + observability attribution (Phase 6) are shipped.

**Source files:**
- `data/seeds/app.App/definition.yml` — doctype definition
- `data/seeds/app.App/script.lua` — lifecycle hooks (`create` hook autogenerates `client_id`; `update` hook carries the app-scoped guard; both hooks validate `redirect_uris` and the headless coherence rule)
- `data/seeds/app.App/documents.yml` — the seeded `facet-cli` app document
- `data/seeds/iam.Roles/documents.yml` — seeded roles (`admin`, `editor`, `viewer`, plus the scoped roles)
- `data/seeds/core.Domain/documents.yml` — the `app` domain row (added alongside `core` and `iam`)
- `db/migrations/0010_api_keys.sql` — the `api_keys` table, including the nullable `app_id` column + partial index (app-owned keys; folded into the create-table migration pre-release)
- `src/app/service_accounts.cr` — idempotent service-account provisioning for backend apps
- `src/app/api_keys.cr` — app-owned key issue/rotate/revoke/lookup
- `src/app/routes.cr` — `POST`/`GET`/`DELETE /Api/app/:id/api-key`
- `src/oauth/redirect_uri.cr` — `OAuth::RedirectUri` — the `redirect_uris` request-time match (exact + loopback port wildcard); the shape rule itself lives in `Util::RedirectUri` (`src/util/redirect_uri.cr`)
- `src/rbac/grant.cr` — `Grant` value type (target + action declarations)
- `src/rbac/app_scope.cr` — `AppScope` and `EffectiveScope` value types
- `src/rbac/grant_resolver.cr` — pure grant ∩ role resolution
- `src/rbac/auth_context.cr` — `AuthContext#app_grant` and `app_grant_permits?` pre-check (Phase 3)
- `src/rbac/read_enforcer.cr` — read-side Layer-1 pre-check (Phase 3)
- `src/rbac/write_enforcer.cr` — write-side Layer-1 pre-check (Phase 3)
- `spec/app/registration_spec.cr` — create, update, grants round-trip, and RBAC specs (Phase 1)
- `spec/app/api_keys_spec.cr` — service-account provisioning, key issue/rotate/revoke, app-scoped enforcement and attribution specs
- `spec/rbac/grant_resolver_spec.cr` — pure unit tests for the resolution engine (Phase 2)
- `spec/rbac/app_enforcement_spec.cr` — service-layer integration specs (Phase 3)
- `spec/support/app_helper.cr` — `seed_app_doctypes(db)` helper that restores the seeded definitions wiped by the per-example TRUNCATE; `seed_facet_cli_app(db)` seeds the `facet-cli` app document
- `spec/app/cli_app_spec.cr` — `facet-cli` seed round-trip, grant ∩ role resolution, the API-key refusal on the seeded app, the app-scoped guard specs, and the redirect-URI / headless hook specs
- `spec/oauth/redirect_uri_spec.cr` — unit tests for the `redirect_uris` shape rule and the match

## Why grants live in document content

A grant is policy, not secret material. It belongs in the append-only event log exactly as a role's permission manifest does. This gives the system audit of grant changes for free (who widened an app's reach, when, from what), RBAC on editing, Lua validation, and WebSocket invalidation. When confidential clients arrive in a later phase, `client_secret_hash` is the thing that belongs in a side table — secret material must never enter an append-only log that cannot be erased.

Resolution always loads the full grant set, so a child doctype would add nested-route ceremony for no benefit. The `grants` field is cached per request, in the same way role permissions are.

## Fields

| Field | Type | Required | Notes |
|---|---|---|---|
| `slug` | `string` | yes | URL-safe. `^[a-z0-9][a-z0-9-]*$`, max 64. Marked `unique`. Operators `eq`, `match`. |
| `name` | `string` | yes | Shown on the consent screen and in admin listings. |
| `description` | `longtext` | — | Shown on the consent screen. |
| `client_id` | `string` | no | ULID, autogenerated by the `create` hook. Marked `read_only` and `unique`. Not `required` (would conflict with `read_only` at validation time). Present on every stored document because the hook always writes it. |
| `client_type` | `enum` | — | Values `public`, `confidential`. Defaults to `public`. A `public` app is a browser-only client (PKCE + DPoP, consent screen, no secret). A `confidential` app adds a backend component: it signs in through the consent screen like a `public` app and can additionally authenticate as itself through an app-owned API key. Both types appear in the launcher. |
| `redirect_uris` | `array(string)` | — | Absolute URIs. Any other `*` is rejected at write time by the Lua hook. See `Util::RedirectUri` and `OAuth::RedirectUri`. |
| `allowed_origins` | `array(string)` | — | Origins permitted for CORS on the token endpoint and the API. Each entry is a bare origin (scheme + host + optional port). |
| `status` | `enum` | — | Values `draft`, `active`, `disabled`. Defaults to `draft`. |
| `no_launcher` | `boolean` | — | Defaults to `false`. When true, the app never appears in the dashboard launcher. For headless registrations — a CLI tool is reached through its client. |
| `no_asset` | `boolean` | — | Defaults to `false`. When true, the app is not a deploy target: the deploy route refuses it, and the Lua hook rejects a `host` (nothing is ever served). |
| `compatible_roles` | `array(string)` | — | Optional list of `iam.Roles` ids. **Metadata only** — used to filter the launcher. Never consulted during authorization. |
| `owner_id` | `reference` to `iam.Account` | — | Used for listing and launcher scoping. Not a permission grant. |
| `service_role_id` | `reference` to `iam.Roles` | — | The role a backend app authenticates as. Set from the wizard's permissions step, or from the app's Settings tab when an app flips to `confidential` after creation; the key-issuance path pins it as the service account's single role. Effective permission is grant ∩ role, computed per request. |
| `service_account_id` | `reference` to `iam.Account` | — | The machine identity (`service_account: true`) a backend app authenticates through. Written by the key-issuance path only; absent for frontend apps. |
| `active_deployment` | `reference` to `app.Deployment` | — | The build served at this app's host. Written by the deploy route's activate step; rollback is a PATCH pointing at an older deployment. Absent until the first deploy. |
| `host` | `string` | no | Exact hostname Facet serves the app at (e.g. `hr.app.company.tld`). Marked `unique`. Optional: an app without a host is never dispatched. Shape and reserved-host rules are in the Lua hooks; see "Deployment serving". Edited on the app's Settings tab (optional; empty clears it) or with a plain `PATCH app.App` — every channel passes the same hook validation. The Overview surface shows it read-only, and the deploy flow sets `active_deployment`, not `host`. DNS records and TLS certificates are the deployment stack's responsibility (nginx or Caddy). |
| `assistant_enabled` | `boolean` | — | Defaults to `false`. Master switch for the app's assistant (see "Per-app assistant"). |
| `assistant_prompt` | `longtext` | — | Optional app-specific instructions. Baked into the assistant system prompt at conversation creation; empty appends nothing. |
| `grants` | `array(object)` | — | Ceiling on what the app may reach. See below. |

The doctype `display_name` template is `"{{ name }}"`, so an app's projection row is labelled by its own `name` value.

### `grants` item shape

Each entry is an object with two properties:

| Property | Type | Required | Notes |
|---|---|---|---|
| `target` | `string` | yes | Concrete doctype path the grant covers, e.g. `crm.Contact`. Bare doctype names and the global `*.*` wildcard are not accepted; the domain wildcard `domain.*` is refused at authoring time (`422`, code `wildcard_target` — see below). |
| `actions` | `array(object)` | yes | Action declarations. Each object is `{name, required}` — see below. |

Each element of `actions` is an object with:

| Property | Type | Required | Notes |
|---|---|---|---|
| `name` | `string` | yes | Action name. Permitted: `read`, `write`, `delete`, or a named action declared on the target doctype. `write` is an alias expanded to `{create, update}` at parse time by `Grant.from_json`. |
| `required` | `boolean` | no | Defaults to `false`. A `true` value means a role that lacks this action is rejected for the app (see `GrantResolver.role_usable?`). A `false` value means the action is included in the effective scope only when the role grants it; its absence never rejects the role. |

The `target` field is a plain `string`, not a `reference`. Grant targets are doctype paths, not document references — the `{domain}.{Doctype}.{id}` qualified-reference contract does not apply. This mirrors `core.Domain.grants[].doctype`.

Grants are stored verbatim. The `write` alias is **not** pre-expanded in storage: a grant with `{name: "write", required: true}` round-trips through the document API as that same object. `write` is a resolver-side concern (see `Grant.from_json`).

### Authoring gate (`App::GrantsAuthoring`)

`Document::Create` and `Document::Update` run `App::GrantsAuthoring.validate` on every `app.App` write (the doctype-keyed branch, like the `core.DomainGrant` gate). Every `grants` entry must parse as a `Grant` (`422`, code `schema`) and name a **concrete** target: the wildcard form `domain.*` is refused (`422`, code `wildcard_target`, naming the target). An application names the doctypes it uses, one entry each, so the setup-time usability check and the runtime enforcer agree entry by entry, carve-outs included. The structural shape (array of objects, required `target`/`actions`) is validated by the doctype definition's field validation before the gate runs.

### Usability is except-aware

`GrantResolver.role_covers_action?` disqualifies a role permission line whose `except` carve-out covers a concrete grant target: a line `read *.* except core.SystemSettings` does not grant read on `core.SystemSettings` — not at this gate, and not at enforcement (`Permission#matches_path?` refuses carved-out targets). The prefix rule matches enforcement's `matches_except?` (an entry on `core.DocType` also carves `core.DocType.Comment`). An admin-like role (`*.*` with no `except`) satisfies every concrete grant. Row-level `scope` never takes part: the grant asks for action coverage, and the app inherits the service account's row scope. A wildcard grant target keeps the lenient at-least-one reading — content that reaches the resolver without the gate (import) still resolves instead of crashing.

Grant coverage follows the route shape. Nested child routes (`/Api/:domain/:doctype/:id/...`) authorize on the full composition path (`domain.Parent.Child...`), prefix-matched. Flat routes (`/Api/:domain/:doctype`) authorize on the bare doctype path. Sidecar routes keep the host-scoped rule: a host grant implies the sidecar operation. A grant on the bare child doctype serves flat routes only. Member-of children have no flat route, so a bare-child grant never authorizes a nested create — grant the parent (or the full composition path) instead.

An app token cannot read `core.DocType` unless the app holds a `core.DocType` grant. Apps that render enum labels or colours from the definition must hardcode them — or the administrator grants `core.DocType` read.

## Lifecycle hooks

`data/seeds/app.App/script.lua` defines a `create(ctx)` hook, an `update(ctx)` hook, and a `deploy` named-action export.

The `create` hook assigns a ULID to `client_id`:

```lua
function export.create(ctx)
  ctx.root.client_id = util.ulid()
  validate_host(ctx, ctx.root.host)
end
```

`util.ulid()` is the platform's Lua-exposed ULID generator (Crystal-backed, see `Util::ScriptHelpers.ulid`). Each call produces a fresh, time-sortable 26-character Crockford Base32 ULID.

Because `client_id` is `read_only`, callers cannot supply or modify it; the hook is the only writer. A caller that attempts to set `client_id` is rejected at validation time with a `read_only` error (422), before the hook ever runs.

The `update` hook enforces `slug` immutability, the app-scoped guard (see Quirks), and `host` validation:

```lua
if ctx.patch and ctx.actor and ctx.actor.app_id then
  for _, field in ipairs({ "grants", "service_role_id", "service_account_id" }) do
    if ctx.patch[field] ~= nil then
      ctx.error(field .. " cannot be modified by an app-scoped caller")
    end
  end
end
```

`ctx.actor.app_id` is present only when the caller is app-scoped (a service account acting for an app, through an app-owned API key or an OAuth app token) — see [`lua-engine.md`](lua-engine.md) → ctx.actor. Session callers carry no `app_id` and keep full edit rights.

Both hooks validate the optional `host` field with the same rule:

- **Shape.** A bare lowercase hostname — no scheme, no port, no path, no wildcard characters, max 253 characters. The deployment target supplies the port at serve time; a stored host never carries one. Checked by `util.valid_hostname` (`Util::ScriptHelpers.valid_hostname?`), because Lua patterns cannot express the rule.
- **Reserved hosts.** The value must not name a host Facet itself answers at. The reserved set comes from config (`host`, `base_url`, `artifact_base_url`) plus the loopback literals (`127.0.0.1`, `::1`) through `util.facet_hosts` (`Util::ScriptHelpers.facet_hosts`); the port strip before the comparison is defensive only — the shape rule already refuses a port. There is no `app_hosting:` config section.

The dispatcher's reserved-host fall-through is the defence-in-depth backstop; the hook is the operator-facing error surface.

Both hooks validate the optional `redirect_uris` array with the same rule:

- **Shape.** Every entry is an absolute `http(s)` URI with no fragment, no userinfo, and no query. Scheme rule: https on any host, http on a loopback host only — the native-app loopback carve-out (RFC 8252): the CLI and desktop clients sign in through a local listener without running a TLS stack, and http on loopback never leaves the machine. Checked per entry by `util.valid_redirect_uri` (`Util::RedirectUri.valid_shape?` — the parse is not expressible in Lua patterns).
- **Wildcard.** The only permitted wildcard is a `*` port, and only on an `http` loopback host (`localhost`, any `*.localhost` subdomain, `127.0.0.1`, `::1`) — RFC 8252 §7.3: the OS assigns the local listener's port, so a native client cannot pin it. A `*` anywhere else — scheme, host, path — is rejected.

Request time matches a presented URI exactly, except that a `*`-port entry matches any port; a registered path pins the presented path, an entry without a path matches any. See `OAuth::RedirectUri.match?`.

Both hooks enforce the headless coherence rule on the merged state: a `no_asset` app cannot carry a `host` — it is never a deploy target, so nothing would ever be served.

The `deploy` named-action export exists only to satisfy `ScriptValidator` (every declared action needs a matching export):

```lua
function export.deploy(ctx, args)
end
```

The deploy mutation is not a document action — the multipart deploy route creates the `app.Deployment` document itself and runs no Lua. Declaring the action in `definition.actions` is what makes `deploy` addressable as an RBAC permission and grant action.

## RBAC

App registration uses the standard RBAC model plus one named action:

| Action | Gate site | Notes |
|---|---|---|
| `update` | app document routes (create, edit, key mgmt) | standard model |
| `delete` | delete route | standard model |
| `deploy` | deploy route (`POST /Api/app/:id/deploy`) | named action declared on `app.App`; scope follows the update rules (a scoped permission passes only when the target row satisfies the named scope's `where`) |

| Role | Permissions | Create/Update/Delete apps | Read apps | Deploy apps |
|---|---|---|---|---|
| `admin` (seeded) | `*` on `*.*` | yes | yes | yes |
| `editor` (seeded) | `create`/`update`/`delete`/`read` on `*.*` | yes | yes | **no** |
| `viewer` (seeded) | `read` on `*.*` | no | yes | no |

No dedicated `manage_apps` action exists in this phase. A future phase may introduce one if a stricter "super-user only" gate becomes necessary; the brief's "super-user only in this phase" requirement is fulfilled by the standard model because no production role outside `admin`/`editor` carries create/update/delete on `*.*`.

Read access to `app.App` is unrestricted for any role with `read` on `*.*`, because the registration list and grant policy are non-secret material.

## Seeding

The `app` domain row is added to `data/seeds/core.Domain/documents.yml`:

```yaml
- id: app
  content:
    color: "#7B1FA2"
```

The `app.App` doctype definition and script are seeded from `data/seeds/app.App/` by `Facet::Doctype::Seed.seed` during `db_reset` (the corpus is embedded into the binary at compile time — see [`doctype-system.md`](doctype-system.md)). The seed runner is idempotent.

The seed runner runs in two passes: pass one registers every definition, pass two seeds every directory's `documents.yml` through the real document pipeline (`Document::Create` — validation, lifecycle hooks, display names). Pass two hoists `iam.Roles` ahead of the alphabetical order — roles are the common reference target of seed documents. A seed document that already exists (same projection id) is skipped, never duplicated.

`data/seeds/app.App/documents.yml` seeds the first-party CLI registration:

- id `facet-cli` (fixed, like `iam.Roles.admin`), `slug` `facet-cli`, `name` `Facet CLI`
- `client_type: public` (authorization code + PKCE through the consent screen), `status: active`
- `no_launcher: true` and `no_asset: true` — the registration is headless: never a dashboard card, never a deploy target, no host
- `redirect_uris` — the loopback port patterns `http://localhost:*`, `http://127.0.0.1:*`, `http://[::1]:*`; the CLI binds an ephemeral local port
- no `service_role_id`, no `service_account_id` — the CLI signs in through OAuth, the elected role comes from the consent screen, and the effective reach is grant ∩ elected role. The role must allow deploying applications (all, or a narrower scope)
- grants: `read`/`write`/`delete`/`deploy` on `app.App` (all required) and `read` on `app.Deployment` (required) — the ceiling

`data/seeds/iam.Roles/documents.yml` seeds `admin`/`editor`/`viewer` plus the scoped roles. Every seeded role references only `core.*` doctypes, which the seed runner registers in pass one.

The `production_editor` role lives in the `iam` fixture bundle (`data/fixtures/iam.facet-domain/`), not in the seeds. Its permissions carry `$mine` scopes on `production.*` doctypes. At seed time those doctypes are not registered, and `RBAC::Validator.validate_permissions` rejects a scope alias whose target doctype is unregistered — a seeded `production_editor` would fail the pipeline. The same rejection runs on bundled role rows through the import authoring gate (B-277, see [`portable-domains.md`](portable-domains.md)). Every import chain therefore lands the `production` bundle before the `iam` bundle: `scripts/import-fixtures` encodes the order, and the e2e backend entrypoint (`e2e/docker/backend-entrypoint.sh`) imports the same baseline chain (CRM, production, iam) after `seed:dev`.

For specs, the per-example TRUNCATE in `spec_helper.cr` wipes `projections` (and therefore the seeded `core.DocType`, `core.Domain`, and `app.App` rows). The `seed_app_doctypes(db)` helper in `spec/support/app_helper.cr` restores the definitions, and `seed_facet_cli_app(db)` in the same file seeds the `facet-cli` app document through the same create pipeline (hook-assigned `client_id` included).

## Quirks

### Empty `grants` array round-trips as an empty Hash

When the `create` lifecycle hook runs, `ctx.root` is passed through the Lua VM and back to Crystal. An empty Lua table `{}` is ambiguous (no integer keys), so an empty `grants: []` survives the round-trip as `grants: {}`. Behaviour is equivalent for downstream iteration (both have `size == 0`). Consumers that branch on `JSON::Any#as_a` must check `raw.is_a?(Array)` first, or call `as_h` on the empty case. This quirk applies to any `array` field on a doctype whose Lua `create` hook round-trips the root table.

### `unique` enforcement

The `unique: true` constraint on `FieldDefinition` is enforced by both `Document::Create` and `Document::Update` through the shared `Document::UniqueConstraint` checker, which queries `projections` for an existing non-deleted row of the same doctype with the same value.

- **Create** checks every unique field on the submitted document (`Document::Create.check_unique_constraints`).
- **Update** checks only the unique fields whose value changed in this update, against the merged document, and excludes the target document's own row — so keeping an existing value is always allowed. The check runs on the post-merge state, before the Lua update hook.

Null and absent values are not constrained, and non-scalar (object/array) values do not participate.

### `slug` immutability

`slug` is declared `unique: true` and described as "Immutable after creation", but the schema cannot express "set once at create, never sent via PATCH" — that is a runtime lifecycle concern. It is enforced by the `update` Lua hook on `app.App`, which rejects any patch that includes a `slug` key (regardless of value). The hook reads `ctx.patch` (the partial PATCH body) rather than `ctx.root` (the merged state, which would always agree with the patch for an overwritten field). Mirrors the create-time `read_only` semantic on `client_id`, scoped to PATCH only so create can still write the initial value.

### App-scoped callers cannot widen their own grant

An app-scoped caller (an app's service account — `ctx.actor.app_id` present) holds `update` on `app.App`, so the standard model alone would let it PATCH an app document and widen `grants` or swap `service_role_id` — a privilege-escalation path, since the grant ceiling would become self-modifiable. The `update` Lua hook on `app.App` rejects any patch that carries `grants`, `service_role_id`, or `service_account_id` when the caller is app-scoped — on any `app.App` row, not only the caller's own. Operators (session callers, no `app_id` on the actor) keep full edit rights. The check reads `ctx.patch`, not `ctx.root` — presence of the key in the patch is the attempt.

## Grant resolution engine (Phase 2)

`RBAC::GrantResolver` is the pure, I/O-free intersection of an `app.App` grant set with an `ActiveRole`. It exposes two functions; neither touches the database, the doctype definition store, or the scope expander.

### `GrantResolver.role_usable?(app, role) : Bool`

Strict-ALL across required grant actions. Returns `true` if and only if, for every `Grant::Action` flagged `required: true` on every grant entry on the app, the role grants the action on a doctype the grant covers. One missing required action ⇒ `false`. Optional actions never reject.

The `write` alias is expanded by `Grant.from_json` into `create` + `update` declarations: a required `write` is satisfied only when the role grants **both** `create` and `update` on a covered doctype. A role's `*` action (`Permission::WILDCARD_ACTION`) is treated as covering any concrete grant action.

### `GrantResolver.resolve(app, role) : EffectiveScope`

The granular intersection. For each grant entry:

1. Finds every role `Permission` whose `(domain, path)` the grant covers (`Grant#covers?`). A `domain.*` grant collects role permissions on every `domain.X` doctype the role holds; a `domain.Doctype` grant also matches a role permission on a descendant path (e.g. `crm.Contact` covers `crm.Contact.Comment`). A role permission on `*.*` (admin) matches every grant target — the admin role reaches every doctype, and the grant is strictly a ceiling.
2. Groups the matching permissions by their resolved entry coordinates (`GrantResolver.entry_coordinates`). Concrete role permissions group on the role permission's `(domain, path)`. A wildcard role permission (`*.*` or `domain.*`) collapses onto the grant's de-wildcarded target — the entry's `(domain, path)` is the grant's, not `*`.
3. For each group, computes the covered actions: each declared grant action name (post `write` expansion) is included when at least one matching permission grants it. Optional actions the role does not cover simply do not appear in the entry's `actions` set; they never cause the entry to be dropped.
4. Emits the entry unless its covered actions set is empty (the role covers the doctype but none of the granted actions).

### `EffectiveScope::Entry`

Each entry pairs the concrete (de-wildcarded) `(domain, path)` with:

- `actions : Set(String)` — the concrete action names (post `write` expansion) the role permits.
- `permissions : Array(Permission)` — the matching role permissions, verbatim. **Scope aliases are preserved as-is.** Resource scope (`$<named_scope>`, `$<context_set>` references inside the named scope's `where`) is **not** intersected with the grant — the grant narrows the set of `(domain, path, action)` the token may attempt at all; it never widens or relaxes a row-level filter. The Phase 3 service-layer enforcer will run scope predicates exactly as today.

### Scope pass-through invariant

A role whose permission carries `scope: ["$mine"]` surfaces that scope alias unchanged on the matching `EffectiveScope::Entry#permissions`. The grant resolver does **not** call `ScopeExpander`, `ContextResolver`, or the doctype definition store. The role's scope predicates survive into the app token unchanged.

### Wildcards, before intersection

Wildcards **expand before intersection**. A grant with `target: "crm.*"` does not emit a wildcard entry — it emits one entry per concrete `crm.X` doctype the role actually holds a permission on. If the role has no permission on any `crm.*` doctype, the wildcard grant produces no entries. The actions it declared become unreachable through this token; if any were `required`, `role_usable?` already returned `false` and the token would not be issued.

The global `*.*` wildcard is **not** accepted as a grant target (`Grant.from_json` raises `ArgumentError`). A grant always names a concrete domain; the admin role reaches everything via its own `*.*` permission, and the grant is strictly a ceiling.

## Layer-1 enforcement (Phase 3)

Phase 3 wires the resolved `EffectiveScope` into every document service so that an app-scoped identity is correctly constrained everywhere a `(domain, doctype, action)` operation runs. No transport, no OAuth, no token issuance is involved in this phase — an app-scoped `AuthContext` is constructed by hand from a real role and a resolved `EffectiveScope`.

### `AuthContext#app_grant`

`RBAC::AuthContext` carries an optional `app_grant : EffectiveScope?`. Existing tokens (`AuthContext.system`, `AuthContext.authenticated`, `AuthContext.denied`) all default `app_grant` to `nil` — every non-app request is unaffected, and the pre-check is a single nil test in that case.

A new factory constructs an app-bound principal:

```crystal
role = ActiveRole.from_projection_content(role_projection.content)
app = AppScope.from_content(app_id, app_projection.content)
grant = GrantResolver.resolve(app, role)
ctx = AuthContext.app_scoped(account_id, role, grant)
```

The constructor enforces that a `Principal::System` never carries an app grant — internal callers (migrations, projection triggers, replication, the AI assistant) are never app-scoped.

### `AuthContext#app_grant_permits?(action, domain, path) : Bool`

Pure, I/O-free pre-check consulted by both enforcers before the role's own `can?` query. Contract:

- **No app grant attached** (`app_grant.nil?`) — passes immediately. The role's own `can?` continues to gate the operation exactly as before. Cost: a single nil test.
- **Present but empty `EffectiveScope`** — fail-closed denial. A usable role (i.e. one that satisfies every required action) never produces an empty scope, so this guards against a present-but-unresolvable grant reaching a service.
- **Present and non-empty** — the grant must contain at least one `EffectiveScope::Entry` whose concrete `(domain, path)` is a prefix of the target path and whose `actions` set includes the queried action. The prefix match mirrors `Grant#covers?` so a grant resolving to `crm.Contact` permits operations on the descendant doctype `crm.Contact.Comment`.

The queried path depends on the route shape. A nested child route (`/Api/:domain/:doctype/:id/...`) is checked against the full composition path (`domain.Parent.Child...`), prefix-matched. A flat route (`/Api/:domain/:doctype`) is checked against the bare doctype path. A sidecar operation is checked against the host's path — a host grant implies the sidecar operation. A grant on the bare child doctype serves flat routes only; grant the parent (or the full composition path) for nested child operations.

Resource scope aliases on the role's `Permission`s are **not consulted here**. The role's scope predicates survive into the app token unchanged and continue to apply via the existing `ScopeExpander` / `ContextResolver` machinery. The grant narrows which `(domain, path, action)` may be attempted at all; it never widens or relaxes a row-level filter.

### Where the pre-check runs

Every read and write enforcer entry point runs the pre-check **after** the `system?` bypass and **before** the role's `can?` query:

| Enforcer entry point | Action queried |
| --- | --- |
| `ReadEnforcer.authorized?` (single document read) | `"read"` |
| `ReadEnforcer.read_denied?` (single-read class gate, the nested parent gate class check, the sidecar host gate, the audit document-history gate, and the aggregate no-field answer) | `"read"` |
| `ReadEnforcer.parent_authorized?` (nested child route parent gate) | `"read"` |
| `ReadEnforcer.list_denied?` (list / aggregate / export class gate) | `"read"` |
| `ReadEnforcer.list_where_clauses` (composed fan-out surfaces: `Document::Backrefs`, `Document::Resolve`, `Artifact::Refs`, the audit child feed) | `"read"` (denial returns `1=0` — one unreadable doctype narrows to nothing instead of failing the whole response) |
| `WriteEnforcer.authorize_create` | `"create"` |
| `WriteEnforcer.authorize_update` | `"update"` |
| `WriteEnforcer.authorize_delete` | `"delete"` |
| `WriteEnforcer.authorize_action` (named action) | the named action's name (e.g. `"promote"`) |

`Websocket::SubscriptionResolver` inherits enforcement automatically by virtue of resolving through `RBAC::ReadEnforcer.authorized?` — no further wiring is needed.

One route-level rule sits outside this table. The global audit list (`GET|QUERY /Api/Audit`) has no concrete `(domain, path)` to check. It denies every app-scoped identity with `403` — see [Structural safety](#structural-safety).

### Fail-closed behaviour

A `Real` principal with a present-but-empty `EffectiveScope` is denied on every operation with 403: single-document reads, list and aggregate queries, export, and create / update / delete / action all answer the same class-level denial. The 403 says the caller holds no permission for the resource class; it never says whether a specific document exists.

### Structural safety

The pre-check lives on `AuthContext#app_grant_permits?`, so the only way an app-scoped identity reaches a document service is via the `AuthContext` struct, and the struct is the only carrier of the grant. The constructor's `Principal::System` guard ensures no internal system-tier caller can carry an app grant — internal bypass paths (`migrations`, `projection triggers`, `replication apply`) are by construction outside Phase 3's reach.

The audit surfaces apply the grant too. The global audit list (`Audit::List` with no `doc_id`) denies every app-scoped identity with `403` before the role check. No grant can cover that view. A grant always names one concrete domain. `Grant.from_json` rejects the `*.*` target. A domain filter does not lift the denial. The rows of one domain include doctypes the grant does not name, so their mutation `arguments` would leak. Document history (`doc_id` present) checks the target doctype through `ReadEnforcer.read_denied?` and `ReadEnforcer.authorized?`. History inside the grant reach answers rows. History outside answers the class-level `403` or the non-disclosing `404`. [`Audit::Rollback`] routes through `WriteEnforcer.authorize_update`, so the grant constrains every rollback write.

### Why grants live in document content

Carried over from Phase 1. A grant is policy, not secret material: it lives in the document so its changes are audited, RBAC-checked on edit, and WebSocket-invalidated. When confidential clients arrive in a later phase, `client_secret_hash` is the thing that goes in a side table — secret material must never enter an append-only log that cannot be erased.

## Dashboard launcher

`IAM::AppLauncher.launcher_apps(db, role_name) : Array(AppSummary)` is the read-side consumer of the grant resolution engine that powers the dashboard's Applications widget. It returns every `app.App` registration the dashboard may show, each flagged with whether the active role can actually use it. Two conditions decide whether an app appears at all:

1. **Enabled** — `status == "active"`. A `draft` app exists but is not launchable; a `disabled` app suppresses issuance and API access. Key issuance itself does not check the status, so a key issued while the app is still in `draft` authenticates only after the app becomes `active` — until then every request answers the uniform `401`, and the server log carries the reason (`app-owned API key refused: app status is draft, expected active`).
2. **Visible by design** — `no_launcher: true` removes the card (a headless registration is reached through its client). Client type does not filter: a `confidential` app signs in through the consent screen like a `public` app, so it gets a card too.

Each returned card carries `usable: Bool` — the `GrantResolver.role_usable?` verdict (the role covers every `required` grant action across every grant entry). A card with `usable: false` still renders in the dashboard, muted and non-interactive, with a notice telling the member their role does not meet the app's requirements — a silent hide left the member no way to see the app existed or to ask for access. The `compatible_roles` field on `app.App` is metadata only and is **not** consulted by the launcher — see [Fields](#fields). Effective permission is always grant ∩ role.

The launcher returns only the public, non-secret fields a dashboard card needs: `id`, `slug`, `display_name`, `description`, `usable`. `client_id`, `redirect_uris`, `allowed_origins`, and `grants` are intentionally absent.

The HTTP route is `GET /Api/iam/apps` (AuthHandler-protected, session-gated). See [`iam.md`](iam.md) → HTTP Routes.

**Source file:** `src/iam/app_launcher.cr`

## Backend apps — service account + API key

A `confidential` app has a backend component and can also act as a machine caller. The service identity authenticates with `Authorization: Bearer fct_…`, where the key is a row in the existing `api_keys` table tagged with the app id. The key authenticates the app's **service account** — an `iam.Account` with `service_account: true`, `status: "active"`, and exactly one role (the app's `service_role_id`, pinned both in `roles` and as `default_role`). Effective reach is grant ∩ pinned role — the same `app_scoped` contract an interactive app gets, re-resolved per request.

Key issuance is keyed on `client_type`: `App::ApiKeys.issue` refuses a non-`confidential` app (422 "App is not a backend app"). The first-party CLI registration is `public` and holds no service identity — the CLI signs in through OAuth, and the elected role comes from the consent screen.

There is no parallel key subsystem: no new table, no new token format, no second verify path. `api_keys.app_id` (part of migration `0010_api_keys.sql`, `NULL` for self-service keys) is the only storage addition, and keys never enter the event log — the established credential precedent.

### Provisioning (`App::ServiceAccounts`)

`ServiceAccounts.ensure(db, app_id, slug, display_name, role_id)` is idempotent: it returns the linked `service_account_id` when live, otherwise it provisions the account (email `svc.<slug>@apps.facet.invalid` — `.invalid` can never receive mail, which is the point) and writes the `service_account_id` back-link on the app document, all in the caller's transaction. Created with the system principal, the same precedent as OIDC JIT provisioning — the operator's authorization happened at the route, and no role grants `iam.Account` creation on behalf of an app.

### Key lifecycle (`App::ApiKeys`)

| Route | Service | Behaviour |
|---|---|---|
| `POST /Api/app/:id/api-key` | `ApiKeys.issue` | Provisions the service account, re-pins its role, revokes any active key, issues the new row (`account_id` = service account, `role_id` = `service_role_id`, `name` = `"app:<slug>"`, `app_id` = the app's projection id) — one transaction. Issuing with an active key present is a **rotation**; one active key per app is route-level policy. The app's `service_role_id` must carry the `api` connectivity channel — issuance refuses with 422 otherwise (the service account authenticates as exactly that role, so a browser-only role cannot hold a key). Returns `{id, key, display_prefix, service_account_id, role_id}`; `key` is the raw token, shown exactly once. |
| `GET /Api/app/:id/api-key` | `ApiKeys.active_key` | `{active: true, id, display_prefix, role_id, created_at, last_used_at}` or `{active: false}`. Never secret material. |
| `DELETE /Api/app/:id/api-key` | `ApiKeys.revoke` | Soft-revokes the active key. Idempotent (`{revoked: bool}`). |

All three routes are **operator-session only**: a real principal that authenticated through neither the API-key nor the app-token channel (`403` otherwise — a key can never mint or revoke itself), CSRF-checked, and gated by the standard model (`update` on `app.App` for the mutations, `read` for the status). The routes are registered in `src/app/routes.cr` before the REST catch-all.

### Diagnosis: every route 401s with a valid key

An app-owned key fails closed with the generic `401` when the pinned service role no longer covers every **required** grant action — grant `write` means role lines `create` **and** `update` (or one `*` line); a role line `create` alone does not satisfy the pair (`GrantResolver.role_usable?` runs before every request's scope resolution). The response body names nothing — anti-enumeration: a leaked key must learn nothing about role state.

The server-side signal replaces the body's silence: the auth handler logs one WARN line naming the role id, the app id, the key id, and the missing actions (`GrantResolver.missing_required_actions`, e.g. `update on fin.Invoice`), and tags the span with `auth.refused = role_unusable`. An operator who sees "every route 401s" reads the log line, then either widens the service role's permission lines or narrows the app's grants. The same WARN fires for the defense-in-depth branch (usable role, empty resolved scope) with `auth.refused = empty_scope`.

## Per-app assistant

An app can offer its users an AI assistant scoped to the app. Two content fields turn it on and tune it: `assistant_enabled` (default `false`) and `assistant_prompt` (optional app-specific instructions). The app's admin edits both on the app's settings tab; the settings save path is the standard PATCH, gated by `update` on `app.App`. Both client types may enable the flag — a `confidential` app signs in through the consent screen like a `public` app, so its browser hosts the chat.

A conversation of the reserved `app` kind is created through `POST /Api/assistant/app/conversations` (`App::Routes`, `src/assistant/app/routes.cr`). The route chain is CSRF → authentication (`401`) → `App::Gate` → create; the body carries `language` only, and every denial answers as clean JSON before any SSE headers. `App::Gate` (`src/assistant/app/gate.cr`) reads the app projection live — the same read the grant resolution runs — and refuses with `403` when the app is absent, `assistant_enabled` is off, the caller carries no `app_id` (a main-app session user), the caller's token names a different app, or the active role's connectivity excludes the `assistant` channel. The stream route re-runs the gate per message, so a channel flip or a role change applies on the next message.

The conversation context (`{"kind": "app", "created_by", "app_id"}`) is built server-side from the authenticated caller — never from the body. The toolset is the full shared registry minus `ping` (`App::Registrar`); every tool call inherits the caller's app token, so the app's grant ceiling bounds each write — the boundary guarantee. The prompt assembly order is the static body, `## Session context` (app name, role, UTC date, boundary line), `## Language`, `## App instructions` (the `assistant_prompt` field), `## Custom instructions`. All baked once at creation.

Host applications embed the chat through the `@facetapp/chat` package — see [`packages/chat.md`](../packages/chat.md).

## Deployment serving

Facet serves an app's static build at the app's own host. The build is **data, not config**: an `app.App` document carries `host` and `active_deployment`, and the dispatcher resolves hosts from live document state, so a new app goes live without a restart or a config change. An app without a `host` value is never dispatched.

`host` is edited on the app's Settings tab or with a plain `PATCH app.App` — any caller holding `update` on `app.App`; the create and update hooks validate every channel the same way (shape, reserved hosts, uniqueness, the `no_asset` coherence rule). Clearing the field is a `null` patch value (JSON Merge Patch removal). The setup wizard collects no host, the Overview surface shows it read-only, and the deploy flow writes `active_deployment`, never `host`. DNS records and TLS certificates stay the deployment stack's responsibility — Facet serves through the operator's reverse proxy (nginx or Caddy); the HostAsk endpoint below exists only for Caddy `on_demand_tls` setups.

### The `app.Deployment` doctype

One deployment document per uploaded build (seeded from `data/seeds/app.Deployment/`). Fields:

| Field | Type | Required | Notes |
|---|---|---|---|
| `app_id` | `reference` to `app.App` | yes | Injected by the deploy route from the URL; a caller value is overwritten. Operators `eq`. |
| `revision` | `integer` | yes | Max + 1 per app, computed by the deploy route. Marked `read_only` — the route is its only writer. |
| `note` | `string` | no | Human label, e.g. "fix login bug". |
| `spa` | `boolean` | no | Defaults to `true`: unknown request paths fall back to `index.html` for page loads (Fetch Metadata navigation, or no header); asset fetches get a 404. |
| `files` | `array(object)` | yes | One entry per file: `{path, file}`. `path` is the URL path relative to the app root; `file` is the artifact id. |

### The deploy route (`src/app/deploy.cr`)

`POST /Api/app/:id/deploy` is a multipart create: the `$content` part carries the deployment JSON, one part per file named `files[<i>].file`. `Artifact::Multipart.parse` + `upload_files` spool, decide the mime (file-name extension first for deploy files, magic bytes as fallback), upload, substitute artifact ids, and write owner rows inside the create transaction — a failed file rolls the whole deploy back.

The route accepts `activate: true` (query string or `$content`) and flips `active_deployment` on the app inside the same transaction: one request is one atomic deploy. Rollback = activate an older deployment (a plain `PATCH app.App`).

One gate for every caller — "your grant ∩ role carries `deploy` on `app.App`":

```crystal
RBAC::WriteEnforcer.authorize_action(db, "app", "App", app_id, "deploy", ctx)
```

| Caller | Credential | Check |
|---|---|---|
| Dashboard operator | session cookie | CSRF header + `deploy` on `app.App` (standard model) |
| CLI / automation | `Authorization: Bearer fct_…` or an OAuth app token | no CSRF; `deploy` must sit in grant ∩ role (Layer-1 pre-check + standard model) |

`WriteEnforcer.authorize_action` follows the named-action rules: a scoped permission only passes when the target row satisfies the scope's `where`, and an app-scoped caller additionally needs the action inside its grant ceiling (the `AuthContext#app_grant` pre-check inside the enforcer). Key liveness (including the active-app gate) ran in `AuthHandler`; the route never re-verifies the token shape.

After the gate, the route refuses an app whose `status` is not `active` (422) and an app marked `no_asset` (422 — a headless registration is not a deploy target; see [Fields](#fields)).

The route writes `app_id` itself from the URL path and passes it as a trusted reference field (`trusted_reference_fields`), so the create's reference check resolves that row under system authority. A caller holding `deploy` on `app.App` therefore deploys without a separate `read app.App` grant — the gate on that exact row already ran.

Behaviour notes:

- A role without `deploy` (e.g. the seeded `editor`) can no longer deploy. The dashboard deploy button disappears for that role until the roles fixtures are revamped.
- An OAuth app token is no longer refused. Its auth context carries the account's active role, and the same `deploy` gate applies. Uniform by design.
- An app that deploys **itself** needs `deploy` in its grants and its service role — the old "self-deploy needs no grants" contract is gone. No legacy data exists; this is a clean break.

The mutation goes through `Document::Create` (`skip_authorization` — the route's own gate ran; `allow_system_writes` — `revision` is read-only), so event sourcing, WebSocket invalidation, and audit attribution hold: the actioner is the operator account or the service account, and `meta.app` carries the app id.

The `files[].path` values are validated against a safe-path rule: no leading `/`, no `..`, no empty segment, valid UTF-8, max 1024 characters. Every entry must carry an artifact id from this request's file parts (caller-supplied `file` values are stripped before upload).

### Host dispatch (`src/app/hosting.cr`)

`App::Hosting::Handler` is a Kemal handler registered before every other handler in `HTTP::Server.routes`. Dispatch order is fixed:

1. **Facet's own hosts win.** If the request hostname equals the configured `host`, `base_url`, or `artifact_base_url` host, or a loopback literal (`127.0.0.1`, `::1` — internal SSR fetches and probes reach the backend by IP), the request falls through to the main router untouched — before any app lookup.
2. **Exact-match lookup.** The request hostname (lowercased, port stripped by Crystal) is matched against the `host` field of `app.App` — a literal compare, never a suffix match. A stored host is a bare hostname; the deployment target supplies the port at serve time. Miss → bare 404, no detail.
3. **Resolve and serve.** app (live, `status == "active"`) → `active_deployment` → files map → artifact bytes.

The `spa` flag scopes the shell fallback to page loads: on a path miss, a navigation request (`Sec-Fetch-Mode: navigate` for top level, `nested-navigate` for an iframe, or no Fetch Metadata header at all — old browsers and command-line tools) gets `index.html`, while an asset fetch (`cors`, `no-cors`, `same-origin`, `websocket`) gets a bare 404. A missing asset must never come back as 200 HTML: with `nosniff` the browser reports a MIME failure instead of a missing file, and the real cause — the path is not in the deployment's `files` map — stays hidden.

Host resolution is cached in `App::Hosting::HostCache` (host → app_id), an invalidate-only cache in the `OAuth::OriginCache` pattern: `Event::Subscriber::AppCache` marks it stale on every `app.App` mutation, and the next request rebuilds it from the DB. No restart is needed when an app sets or moves its host. A fanout lost during a Redis outage is bounded by `cache.staleness_ttl_s` — reads past the bound rebuild without a fanout (see `doc/backend/replication.md` → `Event::Subscriber::DoctypeCache` → staleness bound).

Serving headers: `Content-Type` from the stored `mime_type` (decided at upload time — file-name extension for deploy files, magic bytes otherwise), `X-Content-Type-Options: nosniff`, and a two-tier cache policy: the app shell — `index.html`, the root document and every navigation fallback hit — serves `public, no-cache` (browsers revalidate before reuse, so a deploy is visible on the next navigation instead of up to a max-age later), every other asset serves the conservative `public, max-age=300` ("path contains a content hash" is not a contract the deploy surface enforces). No restrictive CSP and no `Content-Disposition`: this is the app's own site.

**Serving is not the grant layer.** A published build is public by design: any visitor who can reach the app's host gets the bytes. The app pointer is the authorization, not a password — owner rows are still written at upload time, but serving never walks ACLs, so the hot path stays two indexed reads plus one store read. Anonymous calls to the app host answer `200`; the app answers nothing about who is asking.

Public serving is a supported shape, not a gap. The auth posture is the app's own decision, and both extremes are intended: an app that needs authenticated access enforces it itself (its API calls carry tokens and the API's RBAC answers 401; the app's client redirects to login), and an app that faces the public — a job board with anonymous read over active postings, for example — serves its content to any visitor. The serving layer never inserts an auth wall in front of a build. An organization that wants its app private hosts it where only its people can reach — inside the VPN, or behind a network gate — because the serving layer offers no per-app login wall.

What public serving exposes is the app's **frontend source**: the shipped HTML, JavaScript, and CSS. That source can hint at the backend schema (field names a form posts, endpoints it calls), never at data — the data sits behind the API's RBAC. Treat a deployed build as readable by anyone who can resolve the host.

Cookie isolation does not come from config: Facet's session cookies are host-only (no `Domain` attribute), so Facet and an app never share a cookie surface. The reserved-host check keeps an app from being served *at* Facet's origin, where those cookies live. Suffix-style hosts (`*.app.company.tld`) are an ops convention — one DNS record, one certificate, sibling isolation — not an enforcement rule.

### On-demand TLS ask endpoint (`src/app/host_ask.cr`)

`App::HostAsk` serves `GET /Edge/HostAsk?domain=<name>` — the Caddy On-Demand TLS permission endpoint (`on_demand_tls { ask … }`). Caddy's catch-all site block issues certificates at the first TLS handshake for an unknown SNI name; before it issues, it calls this route and reads the status: `200` approves (internal CA on local names, ACME on public ones), any other status denies — the handshake fails with a TLS error and an unapproved host never produces an HTTP request. The wire contract is Caddy-fixed: the queried name rides the `domain` query parameter, and 2xx means approve.

Approval logic: the name is normalized (`Util::ScriptHelpers.normalize_host` — lowercase, scheme/port stripped, one trailing dot stripped), rejected when it is a reserved Facet host (`Util::ScriptHelpers.facet_hosts` — configured hosts, loopback literals, the `backend` service name; the main vhost has an explicit site block and never triggers on-demand, the guard is defence in depth), then resolved through `App::Hosting::HostCache.app_for_host` — the same in-memory, event-invalidated cache host dispatch uses, so an unknown-host handshake storm costs no per-request database read. Public route (`AuthHandler::PUBLIC_ROUTES`, GET); no body, no cookies, one query parameter, no state change. Spec: `spec/http/app_hosting_spec.cr` → "HostAsk endpoint".

### Verification and the request path

`IAM::ApiKey.verify` gains one check for app-owned rows: the named `app.App` projection must be live and `status == "active"` (mirroring the OAuth branch's app gate). `Verified` carries `app_id` + the app's content. `AuthHandler.build_api_key_auth_context` branches on `verified.app_id`: app-owned keys run the exact `build_app_auth_context` sequence (`AppScope.from_content`, `role_usable?`, `resolve`, fail-closed on empty) and build `AuthContext.app_scoped` — so `mutations.app` attribution and audit work unchanged, with the service-account `actioner_id` telling "the backend app did it". The `api_key_id` rides on the context (a request authenticates through exactly one channel): the mutation is stamped on the `app_api_key` channel with both `app` and `api_key` set, so "which key wrote this" is answerable for backend automation too. It also lands on the span: `auth.type = "api_key"`, `api_key = <id>`, `app = <app_id>`. Plain self-service keys behave exactly as before (`api_key` channel, no `app`).

One guard protects the attribution from the ambient browser session: an Authorization header that is present but fails to parse (an empty bearer token — the shape a client sends when the key variable is unset — a raw token without a scheme, an unknown scheme) fails closed with 401. The `auth_token` cookie never rescues a broken explicit credential; the cookie fallback serves only a request that presents no credential at all. Without the guard, an app-key request sent from a browser-session context (the dashboard origin always ships its cookie) would inherit the human's session and write audit rows attributed to the human — machine writes masquerading as a person. The header-wins precedence and the fail-closed rule are pinned at the attribution level in `spec/app/api_keys_spec.cr`.

The developer contract is the standard REST surface: `Authorization: Bearer fct_…`, same error shapes, same filtering grammar as [`rbac.md`](rbac.md). Effective permissions = grant ∩ pinned role.

**Source files:** `src/app/service_accounts.cr`, `src/app/api_keys.cr`, `src/app/routes.cr`; specs in `spec/app/api_keys_spec.cr`.

## OAuth authorization code + PKCE (Phase 4)

Phase 4 puts the resolved `EffectiveScope` behind a transport: an app can obtain an ES256 JWT (`typ: "app"`) by running the standard OAuth 2.0 Authorization Code + PKCE flow against `/OAuth/...`. The full surface (endpoints, claims, DPoP token binding, security properties, CORS, origin cache, app cache subscriber) is documented in [`oauth.md`](oauth.md) — a browser app must present DPoP proofs on every API call, so read its [DPoP section](oauth.md#dpop-sender-constrained-tokens-rfc-9449) before writing the sign-in client. What this section adds is the Phase 3 ↔ Phase 4 contract:

- The token endpoint re-runs `GrantResolver.role_usable?` and `GrantResolver.resolve` against the **live** `app.App` projection at token time, not the one seen at authorize time. A grant narrowed between authorize (≤60s earlier) and the token exchange yields `invalid_grant` and the code is single-use-consumed.
- The app JWT carries the elected role name in `role` (a real `iam.Roles.name`, unmodified). There is no "compounded role" and no role synthesis — exactly one role is active per app session, and the account elects it on the consent screen.
- The consent screen is **always** displayed. An account may hold several roles in Facet, and signing into an app explicitly elects one. There is no consent store and no "silent consent because you consented before" path.
- `AuthHandler` branches on JWT `typ: "app"`. On every protected API request it reloads `app.App` (gates on `status == "active"`), re-resolves the grant, and constructs `AuthContext.app_scoped`. The grant is never cached on the token — it is re-resolved from live `app.App` content so a grant change applies on the next request without re-issuing the token.
- The endpoints live under `/OAuth/...`, not `/oauth/...`. Facet is **not** a general OAuth provider for arbitrary third parties; the endpoints serve Facet-registered apps only.

## Audit and observability (Phase 6)

Phase 6 makes every app-scoped activity attributable so an admin can answer three questions from the audit log and traces alone: what has this app done, on whose behalf, under which role. The attribution has four parts.

### 1. Mutation attribution (`mutations.app`)

Every mutation made through an app-scoped `AuthContext` records the `app.App` projection id in the typed provenance columns next to the `channel` stamp:

```
channel = "oauth_app", app = "01J0ABCD...", cause_kind = "action",
cause_name = "hire", cause_event = "hired", cause_trace = "01J..."
```

`Mutation::Client` accepts a `provenance : Provenance` parameter on every public method (`create` / `update` / `delete` / `snapshot_mutation`), built once per service call via `Provenance.from(auth_context)`. The channel is `oauth_app` for an app token and `app_api_key` for an app-owned static key — the latter carries both `app` and `api_key`, so "which key wrote this" is answerable for backend automation too. The document services derive the provenance from their `auth_context`:

- `Document::Create` (`create_from_parsed`, `create_document`, `create_domain_instance`)
- `Document::Update` (`call`)
- `Document::Delete` (`call`, `cascade_delete_children`)
- `Document::Action`
- `Doctype::Create`, `Doctype::Update`
- `Audit::Rollback` (the rollback snapshot)

The `mutations.app` column is the only store of the app id on a mutation; the projection row does not carry it.

### 2. `Audit::List` app filter

`Audit::List::MutationRecord` carries the `app : String?` field, read directly from the `mutations.app` column. Two filters are exposed:

| Filter key | Operator | Target | Notes |
|---|---|---|---|
| `app__eq` | `=` | `mutations.app` | Returns only the mutations made through the named app |
| `app__ne` | `IS DISTINCT FROM` | `mutations.app` | Returns only mutations not made through the named app (includes `app IS NULL` rows) |

Because `app` is a typed column on `mutations`, `Audit::List.field_for_filter` passes the filter field through unchanged. The filter is documentary on the HTTP route — clients pass `app__eq=<app_id>` in the query string to scope a global audit query to one app.

### 3. `iam.LoginEvent` app attribution + new event types

`iam.LoginEvent` gained an optional `app : string` field (the `app.App` projection id). `IAM::Helpers.write_login_event` writes the field on every event: `nil` for ordinary browser-session events, the app id for app-attributed events. An admin filters the audit log with `content->>'app' != ''` to see only app activity.

The event enum gained four app-session event types:

| Event type | Written by | Reason |
|---|---|---|
| `consent_granted` | `OAuth::Authorize.issue_code` | An account confirmed the consent screen and elected a role for an app |
| `app_refresh` | `OAuth::Refresh` (success) and `IAM::Refresh` (when `session.app` is set) | An app access token was rotated successfully |
| `refresh_failed` | `OAuth::Refresh` at the 7 live-state revalidation failure sites | Refresh refused: account gone, role unassigned, role gone, app gone, app not `active`, role no longer usable, effective scope empty. The session is killed and the event is written before the raise |
| `layer1_denied` | `IAM::Helpers.write_layer1_denial` (called from the document services) | An app-scoped identity was refused at the Layer-1 grant pre-check. The event is written fail-silent so audit never breaks a refused request. The `details` field carries `"<action> on <domain>.<doctype> refused by app grant"` |

`refresh_reuse` retains its prior meaning; on app refresh paths it now carries the app id in `app` rather than only in the `details` string.

### 4. OpenTelemetry span attributes

The `app` id, the elected `role`, and the `sid` (app session id) are attached to the current OpenTelemetry span inside `HTTP::AuthHandler.build_app_auth_context` before the grant is re-resolved. This puts app attribution on the root `http.server.request` span for every protected API call made with an app token — no separate trace query is needed to find the app behind a request.

`Mutation::Client` also sets `span["app"] = app` on every `mutation.client.*` span when the mutation is app-attributed.

### Scope of attribution (what is NOT app-attributed)

Two scoping decisions keep the audit log honest.

**System-tier maintenance operations are not app-attributed.** `Document::Migrate`, `Document::Copy`, and lazy-migration snapshot markers do not carry `app` even when the work was triggered by an app-scoped read. Migration normalizes storage format and copy publishes a domain; the work is the system acting on its own data, not the app acting on the account's data. The mutation `meta` is silent on `app` in these paths and the OTel span does not set the `app` attribute.

**Layer-1 denials are logged on every primary surface that refuses.** A class-level read denial answers 403 on the flat lists, the aggregates, the single-document reads, and the export, and each refusal logs through `IAM::Helpers.write_layer1_denial` — the same path every write gate uses, so the read side logs with the same parity as the write side. The `1=0` narrowing survives only on the composed fan-out surfaces (`Document::Backrefs`, `Document::Resolve`, `Artifact::Refs`, the audit child feed), where one unreadable doctype must narrow to nothing instead of failing the whole response; that narrowing is silent and stays unlogged. The denial is logged on every write path (`Create` / `Update` / `Delete` / `Action`) too. `Audit::List` and `Audit::Rollback` do not log their refusals. The global audit list denies every app-scoped identity with `403` before the role check. No grant can reach that view. A grant always names one concrete domain. `Grant.from_json` rejects the `*.*` target. Document history and rollback enforce the grant at concrete doctype coordinates. Their refusals stay unlogged too. The enforcers refuse, and these two services write no `layer1_denied` event on any path.

### `AuthContext.app_id`

`RBAC::AuthContext` gained an `app_id : String?` field. It carries the id of the app the JWT named, distinct from `app_grant` (the resolved policy ceiling). The constructor enforces a pairing invariant: `app_id` and `app_grant` are both present or both `nil`. The two fields travel together because the grant's provenance is the app token — one is authentication data, the other is policy derived from it. `AuthHandler.build_app_auth_context` constructs the context via `AuthContext.app_scoped(account_id, role, grant, app_id)`.

Document services read `auth_context.app_id` to thread the app id into `Mutation::Client` and into `IAM::Helpers.write_layer1_denial` / `write_login_event`. No service reads `app_grant` for the id; the grant is policy, not provenance.
