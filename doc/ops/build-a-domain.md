# Build a domain over the API

A recipe for authoring a domain — its doctypes and their documents — with
HTTP calls only. Two paths exist: the **draft loop** (recommended for
interactive authoring; throwaway iteration, diagnostics, version gate on
publish) and the **direct path** (a live domain in three calls; no
iteration surface). Both need a principal that holds `write core.Domain`
and `write core.DocType`. See [`../backend/draft-domains.md`](../backend/draft-domains.md)
for the draft machinery and [`../backend/doctype-system.md`](../backend/doctype-system.md)
for the definition grammar.

Every state-changing call below sends the `X-Requested-With: XMLHttpRequest`
header. The CSRF gate requires this header for a cookie-session request;
a `Bearer` or `DPoP` credential without the session cookie is exempt.
The examples send the header with every call — harmless with a Bearer
token, required with a cookie session.

---

## Path A — the draft loop

### 1. Create a draft domain

```bash
curl -X POST https://facet.example.tld/Api/core/Domain/draft \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -H "X-Requested-With: XMLHttpRequest" \
  -d '{"name": "crm", "description": "Customer relationships"}'
```

`201`. The server autogenerates a `_`-prefixed id (for example `_k3vq…`)
and sets `draft: true`. The `name` you send is the publish target; it must
match `^[a-z][a-z0-9\-]*$`.

### 2. Register doctypes

```bash
curl -X POST https://facet.example.tld/Api/core/DocType \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -H "X-Requested-With: XMLHttpRequest" \
  -d '{
    "doctype": "Company",
    "domain": "_k3vq…",
    "schema_version": 1,
    "fields": {
      "name": {"type": "string", "required": true},
      "owner": {"type": "reference", "doctype": "crm.Person"}
    }
  }'
```

`201`. The body is a full `DoctypeDefinition` — the `domain` value is the
draft's autogenerated id. A reference field names its target doctype with
the `doctype:` key (not `reference_to`). The value must be the qualified
`domain.Doctype` form — the publish target domain (`crm` here), not the
draft id — because after publish the value must match the stored reference
prefix. A bare doctype name is not expanded, and every value of such a
field is rejected at write time.

Repeat per doctype. Child doctypes declare `member_of`; the parent
declares the matching `children` entry — composition is mutual.

### 3. Iterate

Edit with `PUT /Api/core/DocType/:id` and read the diagnostics:

- `GET /Api/core/Domain/:id/check` — every doctype's issues plus
  domain-level ones.
- `GET /Api/core/DocType/:id/check` — one doctype's issues.

Diagnostics are warnings (`reference`, `replicate`, child-target
problems), not blockers — fix them before publish so the live domain
starts clean. A bare (dot-less) reference target is an error, not a
warning: publish would produce a domain whose reference fields cannot be
written to. Drop an abandoned draft with `POST /Api/core/Domain/:id/drop`.
The `DELETE /Api/core/Domain/:id` route refuses drafts and names this route.

### 4. Publish

```bash
curl -X POST https://facet.example.tld/Api/core/Domain/_k3vq…/publish \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -H "X-Requested-With: XMLHttpRequest" \
  -d '{"target_name": "crm"}'
```

Copies the structure into a fresh live domain named `crm` and drops the
draft. Publishing over an existing domain (`overwrite: true`) runs the
version gate — a non-breaking change needs a `schema_version` bump with a
migration, or `$force: true`.

## Path B — the direct path

No draft, no gate: a principal with `write core.Domain` mints a live
domain in one call and registers doctypes against it.

### 1. Create the live domain

```bash
curl -X POST https://facet.example.tld/Api/core/Domain \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -H "X-Requested-With: XMLHttpRequest" \
  -d '{"id": "crm", "name": "crm", "description": "Customer relationships"}'
```

`201`. The body's `id` (or `domain`) key names the domain — a body without
either answers `422`. The creator is auto-granted domain editor. There is
no `/check` gate and no version gate on this path.

### 2. Register doctypes

The same `POST /Api/core/DocType` call as Path A, with `domain` set to the
live name. Full validation applies: named scopes are checked against the
domain's declared context sets.

### 3. Create documents

```bash
curl -X POST https://facet.example.tld/Api/crm/Company \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -H "X-Requested-With: XMLHttpRequest" \
  -d '{"name": "Globex"}'
```

`201`. A child document goes through the parent's nested route:
`POST /Api/crm/Company/:id/Contact` — never a flat create on the child
doctype (it answers `422`).

## Status codes to expect

| Status | When |
|---|---|
| `201` | Domain or doctype created, document created |
| `403` | RBAC denial, or the domain-membership gate (a scoped `create core.DocType` grant requires that you edit the target domain) |
| `404` | Unknown route id (non-disclosing) |
| `409` | Duplicate doctype registration — `POST /Api/core/DocType` for an existing `(domain, doctype)`; edits go through `PUT /Api/core/DocType/:id` |
| `422` | Validation: invalid definition, unknown top-level definition keys (the response names them), named-scope errors, missing domain, child created flat, body `id` on a non-Domain create |

## Machine-readable structure

`GET /Api/openapi.json` serves the declarative OpenAPI slice: document
CRUD, audit history/rollback/restore, the IAM account routes, secret
staging, document import/export, and the platform operator surfaces
(managed indexes, artifact administration, system settings), with status
codes and the write-plane 403 classes. It is authenticated like the other
control-plane GETs. MCP, OAuth, and the assistant stay out of the slice
by decision. Response shapes stay in the backend docs; per-doctype
structure is read live — `GET /Api/core/Domain` (live domains),
`GET /Api/core/DocType` (a domain's doctypes), and each doctype's stored
definition, the same payload `get_schema` serves over MCP. See
[`../backend/openapi.md`](../backend/openapi.md) for the slice's scope and
the drift check, and [`../backend/mcp.md`](../backend/mcp.md) for the
boundary: MCP is the data plane; schema authoring is REST/UI.

## Serving an application over the domain

A bespoke frontend for the domain registers an `app.App` document (slug,
grants, `redirect_uris`, `allowed_origins`, optional `host`), deploys a
build, and signs its users in through the OAuth Authorization Code + PKCE
flow. Sign-in is not plain Bearer: an app that presents a DPoP proof
receives a **DPoP-bound** token, and every API call then needs the
`Authorization: DPoP …` scheme plus a fresh proof header — a Bearer
presentation of a bound token answers `401`. Read
[`../backend/app-system.md`](../backend/app-system.md) for the deploy and
grant model, and [`../backend/oauth.md`](../backend/oauth.md) → **DPoP
sender-constrained tokens** for the proof shape, the `htu` origin pinning,
and the error responses before writing the client.
